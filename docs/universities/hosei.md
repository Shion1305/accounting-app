# 法政: 取引の用途だけでなく領収書提出の文脈が必要

更新日: 2026-09-27

位置付け: 提供サンプルの調査結果。最新の正式規則・運用の確定とは区別する。

[ドキュメント一覧](../README.md)

資料: `docs/hosei/codemate最終提出用.xlsx`。

| 根拠                                            | 確認できた情報                                                                                                          | 保存・入力への影響                                                                                         |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `費目詳細!D3:H5`、`入力例!E5:I15`               | NO.・金額・購入年月日・内訳・用途。購入内容と「どの活動に使うか」は別欄                                                 | 実購入日と用途を取引登録・立替申請で取得し、承認後も保持する。活動日と購入日を混同しない                   |
| `入力例!E9:E15`、`E22:E23` および左側の図形説明 | 既に活動規模の補助金申請で提出した領収書は「規模1～」、正課外の経費補助では「正課外1～」、活動実態では「実態1～」とする | 領収書を提出した制度・区分が必要。費目や金額だけで番号の接頭辞を決められない                               |
| `入力例` のB6:D9付近、I31:AA33付近の図形説明    | 決算書で提出する領収書は「1～」。費目別に領収書をまとめ、領収書上の番号と表のNO.を一致させる                            | 単なる表示行番号とは異なる。物理領収書・提出区分・帳票番号の対応を管理する必要がある                       |
| `費目詳細!I3:K3`、`入力例!J5:L5` と列設定       | 対象金額・対象外金額・備考の列は存在するが、両シートとも非表示                                                          | 入力者、査定対象制度、利用時期、必須性は未確認。利用者が初回登録で必ず対象額を入力する、と決めてはいけない |
| `費目詳細!I108:J108`                            | 対象額系の総計に既存の参照エラー                                                                                        | このファイルの式をそのまま業務仕様にできない。空書式と運用確認が必要                                       |
| `費目詳細!B101:H106`、`入力例` 下部の図形説明   | 教材費・サーバー維持費等の追加費目、費目追加を認める説明                                                                | 固定7種類のプルダウンでは不足する。自由記述を機械推定せず安定した費目コードで扱う                          |
| `入力例!C1` と下部の説明                        | 明細を基にGCSSへ費目別支出を入力し、このファイルも提出                                                                  | これは支出明細のサンプルであり、収入書式やGCSSへの提出完了まで生成だけで満たすとは言えない                 |

具体例: 同じ日付・金額・費目の印刷代でも、今回決算で領収書を提出するものと、活動規模の申請で提出済みのものではNO.の表記が異なる。現状のDBの値だけでは区別できない。取引登録時には「未確認」を許容し、提出時・会計担当の確認時に提出区分を更新できる必要がある。

接頭辞の根拠は明確だが、過去の申請番号をそのまま再利用するのか、区分内でどの範囲まで連番を振るのか、1枚の領収書を複数費目へ分ける際の規則は、このサンプルだけでは確定しない。既知の提出番号や対応は失わず保持し、採番規則は正式な説明で確認する。ページやシートをまたいだ際も同じ領収書との対応を維持する。

## 作成する書類と範囲

| 書類・シート             | 用途                                             | 自動生成する範囲                                                                     |
| ------------------------ | ------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `費目詳細`               | 費目ごとの支出明細。GCSSの決算入力の根拠となる   | 団体名、明細、用途、領収書対応番号、小計・総計。継続形式はQ-04の確認後に確定         |
| `入力例`                 | 入力と領収書整理の説明                           | 参照資料。提出用PDFの出力対象にしない                                                |
| 費目別の領収書整理用紙   | 説明図ではA4へ領収書を貼り、番号を表と一致させる | 対応表・整理順は生成可能。原本整理の完了はアプリが判定しない。専用の正式台紙は未入手 |
| GCSSの決算情報・収入書類 | サンプルの説明にGCSSへの費目入力がある           | このExcelだけでは全項目を確定できない。GCSS送信機能は今回の対象に含めない            |

## 帳票生成へ要求する入力形式（提案）

共通の形式と必須性の読み方は[大学別入力契約](README.md#大学別入力契約の読み方)を参照する。以下の必須性はアプリの提出用出力に対する提案であり、大学の公式な必須欄一覧と同義ではない。

| 入力                                | 型・単位                                                                            | 必須条件・入力時点                                | 根拠／用途                                               |
| ----------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------- |
| `organization.name`                 | 空でない文字列                                                                      | 出力時必須。団体設定                              | `費目詳細!D1`                                            |
| `entries[].occurredOn`              | 確認済みの購入日 `YYYY-MM-DD`                                                       | 各支出で必須。登録・補完時                        | `F3`。申請日時では代用しない                             |
| `entries[].category`                | 安定した科目codeと名称                                                              | 各支出で必須。大学費目へ対応できること            | `B3`と費目別ブロック                                     |
| `entries[].description` / `purpose` | 内訳／用途を別の文字列として保持                                                    | 各支出で非空を要求する案。登録・補完時            | `G3:H3`。片方から他方を自動生成しない                    |
| `entries[].amountYen`               | 正の整数円                                                                          | 各支出で必須                                      | `E3`                                                     |
| `entryDetails[].sourceKey`          | Snapshotの支出キー                                                                  | 補助情報がどの支出に属するかを指定                | 不明なキー・同じキーの重複は拒否                         |
| `entryDetails[].receiptRef`         | 領収書を識別する文字列                                                              | 帳票番号と証憑を照合できる参照が必要              | R2の画像キーそのものを帳票へ出さない                     |
| `entryDetails[].submissionClass`    | `unknown` / `settlement` / `activity_scale` / `extracurricular` / `activity_record` | 提出用出力ではunknownを解消する案。会計担当が確認 | 決算書・活動規模・正課外・活動実態の説明文               |
| `entryDetails[].knownReceiptNumber` | 文字列またはNULL                                                                    | 過去・物理領収書の番号が分かる場合に保持          | 新しい表示順で既知の対応を上書きしない。採番の詳細はQ-03 |
| `entryDetails[].assessment`         | 未判定、または文脈を特定した対象額判定                                              | Q-02で必要と確認されるまで要求しない              | 非表示の`I:J`。対象額が0円でも未判定とは区別             |
| `entries[].note`                    | 文字列またはNULL                                                                    | 任意として保持。出力有無はQ-02で確定              | 非表示の`K`                                              |

`entryDetails` はSnapshot内の型付き `reportContext` に持たせる案。例えば通常提出と既提出を区別する最小の形は次のとおり。番号は合成例であり、公式の採番規則を確定したものではない。

```json
{
  "reportKind": "hosei_expense_details",
  "schemaVersion": 1,
  "entryDetails": [
    {
      "sourceKey": "expense:example-1",
      "receiptRef": "receipt:example-1",
      "submissionClass": "activity_scale",
      "knownReceiptNumber": "規模1"
    }
  ]
}
```

1行と1領収書が対応する場合の案である。分割・複数領収書・複数回提出がある運用はQ-03で確認し、必要なら関連の配列や配賦へ拡張する。これを未確認のままDBの1対1制約として固定しない。

## 計算できる値と不足時の扱い

- 費目小計と支出総額は元取引から算出する。NO.の接頭辞には提出区分が必要で、単純な行番号からは決めない。
- 対象額の二分が正式に確認できた場合だけ、対象外額を総額との差で計算する。
- 購入日・費目・用途・領収書対応が不足した行は、元の支出キーと修正項目を返す。元の申請メモや画像から自動で確定した扱いにしない。
- 入力例を継続シートに流用しない。2枚目以降も費目・番号対応・集計の重複を検証する。
