# 大学書式と追加メタデータの調査

調査日: 2026-09-27

位置付け: 提供資料の監査。最新版の正式規則・運用は別途確認する。

[ドキュメント一覧](../README.md)

## 結論

金額・日付・摘要・一般的な会計項目だけでは、提供された全ての書式を完成させられない。取引に関係する用途・領収書提出情報に加え、年度担当者、活動、補助金、残高内訳が必要な書式がある。

現状のDB・入力画面はこれらを保存できていない。PR #2のnullableな用途・対象額は値の受け渡しまでで、保存や大学別必須判定を保証しない。[現行実装との照合と保存設計](../design/accounting-data.md)を参照する。

共通の要件資料は[会計出力機能の要件定義書 Ver.1.0](../references/accounting-export-requirements-v1.pdf)。④・⑨には主に日付・摘要・会計項目・金額・備考、⑭には大学・年度が挙がるが、実書式には追加の情報が存在する。PDFの項目列挙だけを完全な保存仕様として扱えない。

要件PDFと4大学の調査用参照コピーを同梱し、Excel原本は直接公開しない。法政は`入力例`の領収書画像を除去し、`費目詳細`の全実取引を削除して合成例へ置き換えた。学習院はZIP構造を修復し、各参照コピーから個人・環境等の識別メタデータを除去した。処理内容・確認結果・ハッシュは[参照資料の管理記録](../references/README.md)を参照する。

参照コピーは書式と設計上の根拠を共有するための派生資料であり、大学が発行した最新版の正式テンプレートとして保証しない。既存数式の問題は修正せず記録している。製品用の空テンプレートは年度・正式性を確認して別途採用し、記入済みサンプルや合成例をそのまま提出用にしない。

## 確認方法と限界

4大学・全10シートについて、セル値・数式だけでなく図形内の説明、コメント、非表示列、名前定義、Excel拡張形式の入力規則も読んだ。法政・早稲田・立命館の関連範囲は画像化して配置も確認した。学習院の原本は使用したレンダラーで取り込めず、追加確認でZIPの `[Content_Types].xml` エントリのローカルヘッダ不正を確認した。読み取れたOOXMLを調査根拠とし、同梱する参照コピーではZIP構造を修復している。修復や匿名化の確認と、製品の生成・印刷品質の受入確認は別に扱う。

法政の対象金額・対象外金額・備考は非表示列だった。列の存在を、そのまま利用者の必須入力の根拠にはできない。一方、領収書の提出区分による番号の接頭辞は説明文に明示されている。このように「欄の存在」「記入例」「明示された条件」「未確認の運用」を区別する。

横浜国立・明治が初期対象であることは変わらない。サンプルがある後続大学は構造上の不足を見つけるために調査しており、初期実装の対象追加を意味しない。

## 大学別入力契約の読み方

各大学ページで、作成する書類・追加の入力形式・算出できる値・不足時の扱いを管理する。[横浜国立](yokohama-national.md)・[明治](meiji.md)は書式未入手のため、確定できない事項と確認手順を記載している。

大学別入力は、取得Adapterが組み立てる[AccountingSnapshot](../design/export-pipeline.md)の拡張案である。ブラウザから会計データ本体を自由に指定する出力APIの形式ではない。保存された会計データ・年度プロフィール・関連情報を取得して大学別変換へ渡し、ファイル出力側は変換済みData Frameを受け取る。

| 共通部分       | 形式・意味                                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 団体・年度     | `organization.name`は団体名、`fiscalYear`は提出年度の西暦整数                                                                                           |
| 期間           | `period`のfromを含みuntilExclusiveを含まない。`all`以外では両端を指定する。年度帳票で全期間や月次を提出扱いにできるとは限らず、定義側で適合性を検証する |
| 取引           | `entries[]`。sourceKey、収支区分、取引日、登録日時、整数円の金額、科目、摘要、備考・用途。既存の契約だけで大学別の全入力を表せるとはしない              |
| 残高           | 確認済み開始残高。不明はNULL。0円と区別する                                                                                                             |
| 追加情報       | 型付きの`reportContext`を追加する案。`reportKind`と`schemaVersion`で形式を識別し、大学ごとのprofile・entryDetails等を検証する                           |
| 関連キー       | `entryDetails[].sourceKey`等は同じSnapshotの取引を参照する。未知・重複・他サークルの参照を拒否する                                                      |
| 金額・人数     | 金額は安全な整数円、人数・件数は非負整数。表示用の「円」や桁区切りは含めない                                                                            |
| 日付・識別子   | 日付は`YYYY-MM-DD`、月は`YYYY-MM`。学籍番号・団体コード・電話番号・提出番号は先頭0を失わない文字列                                                      |
| 未確認・非該当 | NULLやunknownは未確認。非該当・未申請・未配置・実額0は確認した事実として区別する                                                                        |

項目表の「出力時必須とする案」はアプリの完全性チェックの提案を表す。大学資料が明記した必須条件、単なる見本、当方の提案を混同しない。型・enum・JSON例も実装済みAPIではなく、正式な入力契約を詰めるための案である。

条件付きの従属フィールドは、非該当を示す状態が別に確定していればNULLを許容する。例えば `hasAdvisor=false` の顧問名NULLは非該当であり、配置有無未確認とは異なる。日付NULLだけで未実施と未確認を区別できない場合は、対応する状態を別に持つ。

元情報の入力責務は[保存設計](../design/accounting-data.md)、書式の保持と継続は[ファイル生成](../design/file-generation.md)、具体的な検証は[テスト戦略](../design/testing.md)で管理する。大学ページに同じDB設計を複製しない。

## 書式を追加・更新するとき

1. 正式な出典・年度・ファイル版を確認する。既存資料との差分はセル・数式だけでなく説明・非表示列・入力規則も確認する。
2. 各欄の意味、必須条件、入力者、入力時期を大学ページへ記録する。未知は未知のまま[未決事項](../plans/accounting-export.md)へ登録する。
3. 登録時に必要な事実、提出準備で補完できる情報、計算できる値を分け、[保存設計](../design/accounting-data.md)に不足がないか確認する。
4. 空テンプレートと匿名の固定データで[出力・再計算・継続](../design/file-generation.md)と[テスト](../design/testing.md)を確認する。
5. シートや説明文の年次不整合、対象外の非会計シート、紙の原本提出等の条件を解消してから対応完了とする。

同じレイアウトなら科目・配置設定を追加できるが、新しい入力事実や帳票構造があれば保存・変換も拡張する。「大学追加は常にマッピングだけ」とは約束しない。
