# 設計ドキュメント

プロジェクトの要件、現在の構成、設計方針、調査根拠、実装順序の入口。仕様は設計ポイントごとに一か所で管理し、関連文書からリンクする。

現在は、LLMが既存のExcel書式を読み、集計・配置・編集まで行う方式を検証している。大学別Data Frameやセル対応表を先に実装する工程は、PoCの結果が出るまで一時停止する。既存の要件・設計・変換実装は品質基準と比較資料として残し、方式検証後に再開・変更する範囲を判断する。

## 最初に読む

1. [用語](../CONTEXT.md) — 承認と精算、取引と申請、生成と提出の区別。
2. [全体構成](design/overview.md) — 現行システムと設計上の境界。
3. [会計出力の要件](requirements/accounting-export.md) — 対象・成果物・受入条件。
4. [LLM直接編集の検証計画](plans/llm-file-editing-evaluation.md) — 現在の優先作業、比較条件、評価と費用の測り方。
5. [実装計画](plans/accounting-export.md) — 全体の進捗、従来方式の工程、未決事項。

初回の有料PoCは、合計10米ドルの予算で `gpt-6.1-sol`、`gpt-6-luna`、`gpt-5.6-luna` を比較した。呼び出しと費用は[計測用ゲートウェイ](design/llm-evaluation-gateway.md)に記録し、実測値・失敗原因・採用判断は[PoC結果](reports/llm-file-editing-poc-2026-10-12.md)へまとめる。初回検証は完了し、47応答の使用量からの推計は$2.924513275。Solは固定条件12回すべてで静的合格・応答完了となった。人が確認する下書き生成の次段階へ進める候補であり、本番の自動提出は未検証。

仕組みと結果を図で確認する場合は、[説明スライド（SVG・PDF・HTML）](reports/llm-file-editing-slides/README.md)を参照する。

生成コードの失敗と、成功したSolの手戻りは[原因分析](reports/llm-file-editing-failure-analysis-2026-10-12.md)へまとめた。保存済み44応答の調査であり、追加プロンプト案の改善効果は未検証。

## 読み方と状態

- **現状**: 確認した基準コミットまたはPRの実装。設計の記載だけで実装済みとは扱わない。
- **合意済み方針**: 実現する対象・責務など、採用した方向性。未実装の場合もある。
- **提案**: テーブル名・API・型など、実装前にレビューする詳細。
- **要確認**: 正式書式・運用・方式検証が不足している事項。推測で決定へ変更しない。
- **調査根拠**: 提供資料から確認できた事実。最新の正式規則と同義ではない。

進捗の正本は実装計画とする。大学ページは書式の根拠、設計ページはその根拠に対するアプリの責務、ADRは採用理由を記録する。

## 更新ルール

1. 仕様を変えるPRで、該当する正本も更新する。本文を別文書へコピーして同期箇所を増やさない。
2. 要件を変える場合は受入条件、保存・出力を変える場合は検証ケースへの影響も確認する。
3. 大学書式を追加・変更する場合は、資料・年度・シート／セル・未確認事項を大学ページへ記録してから必要な入力・保存・出力を見直す。
4. 未決事項は実装計画でID・影響・解消に必要な証拠を管理する。解決時には設計の正本を更新し、解決したPR等を記録する。
5. 変更しづらく、背景がなければ理由が分からない判断には連番のADRを追加する。既存判断を覆す場合は旧ADRをsupersededにして新しいADRへリンクする。日常的な実装選択ごとには作らない。
6. 文書だけのPRでは、相対リンク、コードとの整合、提案と実装済みの区別、差分を検証する。ローカル絶対パス・環境固有値・機微情報を埋め込まない。原資料を含める場合は[大学別資料の管理](universities/README.md)に従い、本文・画像・ファイルメタデータも確認する。テストのfixtureには合成データを使う。

`accounting-export-plan.md` は旧URLからの案内だけを残す。[旧引継ぎ資料](../会計アプリ%20引継ぎ資料.md)は作成時点の記録として保存し、現在の設計の正本にはしない。アプリ利用者の説明文に内部構成を持ち込まず、開発者向けの設計はここで管理する。
