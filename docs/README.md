4. [実装計画](plans/accounting-export.md) — 進捗、小さなPRの順序、未決事項。

## 読み方と状態

- **現状**: 確認した基準コミットまたはPRの実装。設計の記載だけで実装済みとは扱わない。
- **合意済み方針**: 実現する対象・責務など、採用した方向性。未実装の場合もある。
- **提案**: テーブル名・API・型など、実装前にレビューする詳細。
- **要確認**: 正式書式・運用・方式検証が不足している事項。推測で決定へ変更しない。
- **調査根拠**: 提供資料から確認できた事実。最新の正式規則と同義ではない。

進捗の正本は実装計画とする。大学ページは書式の根拠、設計ページはその根拠に対するアプリの責務、ADRは採用理由を記録する。

## 更新ルール

1. 仕様を変えるPRで、該当する正本も更新する。本文を別文書へコピーして同期箇所を増やさない。
2. 要件を変える場合は受入条件、保存・出力を変える場合は検証ケースへの影響も確認する。
3. 大学書式を追加・変更する場合は、資料・年度・シート／セル・未確認事項を大学ページへ記録してから必要な入力・保存・出力を見直す。
4. 未決事項は実装計画でID・影響・解消に必要な証拠を管理する。解決時には設計の正本を更新し、解決したPR等を記録する。
5. 変更しづらく、背景がなければ理由が分からない判断には連番のADRを追加する。既存判断を覆す場合は旧ADRをsupersededにして新しいADRへリンクする。日常的な実装選択ごとには作らない。
6. 文書だけのPRでは、相対リンク、コードとの整合、提案と実装済みの区別、差分を検証する。ローカル絶対パス・環境固有値・機微情報を埋め込まない。原資料を含める場合は[大学別資料の管理](universities/README.md)に従い、本文・画像・ファイルメタデータも確認する。テストのfixtureには合成データを使う。

`accounting-export-plan.md` は旧URLからの案内だけを残す。[旧引継ぎ資料](../会計アプリ%20引継ぎ資料.md)は作成時点の記録として保存し、現在の設計の正本にはしない。アプリ利用者の説明文に内部構成を持ち込まず、開発者向けの設計はここで管理する。
