**Solも、途中の編集処理を修正しながら成功していた。** 最終結果は応答完了・静的評価12/12合格だが、XMLの正規表現、ZIPメタデータの使い回し、古い計算キャッシュなどに手戻りがあった。本稿は追加比較の前に行った原因分析を記録する。この分析を受けた24応答の追試は、[追加指示の比較結果](llm-prompt-improvement-comparison-2026-10-12.md)へ分けて記録した。

## Sol: 成功までに何を修正したか

### 1. 正規表現が隣のセルまで取り込む

立命館r1の#6で、セルを探す正規表現を次のように修正して再実行している。

```python
code = In[5].replace('([^>]*)(?:/>|>.*?</c>)', '([^/>]*)(?:/>|>.*?</c>)')
exec(code)
```

元のパターンは自己終了タグ `<c .../>` を通常の開始タグのように扱い、別セルの `</c>` まで取り込める。早稲田r1の#6〜8では、結合セルの起点G5の罫線スタイルが変わったことを確認し、貪欲なマッチを修正した。学習院r3 #8、立命館r3 #8、早稲田r3 #10などにも類似の修正がある。直前の出力が空の事例では、元の例外名は不明。

**改善候補:** セル・行境界をまたぐ正規表現を作らず、名前空間を保持できるXML編集処理を使う。編集後に「セル参照の行番号＝親rowの番号」「重複参照なし」「対象外セルが不変」を確認する。単にXMLがパースできるだけでは不十分である。

### 2. 元ZIPのメタデータを出力に使い回す

学習院r1 #8では元ZIPを開き直し、書き出しを次の形へ修正している。

```python
out.writestr(copy.copy(info), replacements.get(info.filename, z.read(info.filename)))
```

立命館r1 #7、法政r1 #6・r2 #9、早稲田r1 #10・r2 #10・r3 #11、学習院r3 #12でも、元ZIPを開き直すかメタデータを複製する修正がある。

`ZipInfo` をそのまま別ZIPの書込みに渡すと、元ZIPを読むためのオフセットもメモリ上で書き換わる。合成ZIPの再現ではオフセットが `[0, 36]` → `[0, 135]` へ変わり、その後の元ファイル読込が `BadZipFile` になった。`copy.copy(info)` では元のオフセットが保たれた。**この例外名は最小再現で確認したもので、過去ログに記録された例外ではない。** 出力ZIP自体は正常でも、比較用の元ZIP読込が失敗し得る。

**改善候補:** 出力には複製したメタデータを渡し、独立検証時には元ファイルを新しく開く。処理手順が一定なので、プロンプトだけでなく汎用のZIP書出しヘルパーへ固定する候補でもある。

### 3. 再計算が終了しても、保存値が古い

| Solの試行       | 最初に観測した値                                        | 修正後の値・操作                                                                     |
| --------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 学習院r1 #5〜11 | 入力C18/C19/C5が各10,000なのに、複数の合計キャッシュが0 | 使い捨てコピーの数式キャッシュを除去し再計算。#8でC17=20,000、C26=30,000、G25=25,000 |
| 法政r2 #6〜7    | E107が旧値3,500                                         | キャッシュ除去・再計算後に9,500                                                      |
| 早稲田r2 #8〜10 | C45=0、G44=-6,700、G45=0、B7も元の表示                  | 再計算後にC45=35,000、G44=28,300、G45=35,000、B7も更新                               |

いずれもLibreOfficeの終了コードだけでは古い値を検出できなかった。**改善候補:** 作業コピーの数式キャッシュを無効化し、再計算を要求したうえで、実際の値を入力から独立に計算した合計と照合する。最終ファイルへ移す場合も確認済みのキャッシュだけに限定し、元の式・パーツは保持する。

また、立命館r1/r2、早稲田r1、法政r3の4試行にはLibreOffice実行がない。モデルが計算して書いたキャッシュを `data_only=True` で読み直しても、独立した数式再計算の証拠にはならない。openpyxlのこの設定は保存済み値の読込を切り替えるものと説明されている。[公式ドキュメント](https://openpyxl.readthedocs.io/en/stable/tutorial.html#loading-from-a-file)

前回のローカルExcel確認は別の検証で、Sol各書式r1の4件に限られる。これをSol全12件のネイティブ再計算確認へ拡張しない。

### 4. 探索と自己検証にも削減・改善余地がある

- **ファイル名の仮定:** 全12試行の最初の呼出しが小文字 `skill.md` を読もうとし、保存出力は空だった。立命館r3では一覧取得後に大文字 `SKILL.md` を読み、説明を取得している。パス・大文字小文字の仮定による手戻りが疑われるが、`FileNotFoundError` の保存記録はない。存在確認してから読む指示が候補。
- **大きな出力:** 早稲田r1 #2は59,653文字、r2 #5は65,970文字、r3 #4は68,112文字を1回で出力した。全セルやXMLを繰り返し出す代わりに、シート構成・機能一覧から必要箇所へ絞る。ただし図形内の記入説明や非表示領域を調査対象から落とさない。文字数は課金トークン数ではなく、費用削減効果は未測定。
- **検証を自分で緩める:** 学習院r1 #10〜11・r2 #7〜8・r3 #13〜14では、新規セルE28/H28のデフォルトスタイル表現差を `_style` 比較から除外した。今回は外部評価も合格したが、モデルが変更できる自己検証だけを合否判定にしない。
- **警告と失敗の区別:** 12試行中8件にdconfの権限警告があっても、処理は完了していた。早稲田の入力規則に関する読込警告も、元XMLを保持した出力での規則消失を意味しない。元から存在する法政の参照切れも、新たな破損と分ける。

## 他モデル: 最終失敗へつながった操作

### 5.6 Luna: 依存不足からは復旧したが、保存・記入の問題が残った

比較12件と追加2件はすべて応答完了・ファイル取得済み。比較の静的合格は学習院r1の1件のみだった。

立命館r1 #8と学習院r3 #7には、捕捉した例外を表示した次のログが実在する。

```text
ModuleNotFoundError("No module named 'artifact_tool'")
```

両方とも別ライブラリへ切り替えてファイルを生成した。環境の説明にはそのライブラリが存在する前提の指示があったが、実測と一致しなかった。これは依存不足の証拠であり、全ての不合格を説明する証拠ではない。他の空出力のimport試行まで同じ例外と断定しない。

| -------------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------- |

早稲田の問題の正規表現は次の形だった。

```python
pat = rf'<c\b([^>]*\br="{re.escape(coord)}"[^>]*)>(.*?)</c>|<c\b([^>]*\br="{re.escape(coord)}"[^>]*)/>'
m = re.search(pat, xml, flags=re.S)
attrs = (m.group(1) or m.group(3)).rstrip('/')
```

最初の選択肢が `<c .../>` にも一致し、後続セルの終了タグまで取り込む。`rstrip('/')` は不正な開始タグの修正にはなったが、削除した行境界は戻らない。openpyxlで再読込できた後も、最終成果物に親行不一致が残った。[合成再現スクリプト](../../experiments/llm-export/reproduce-editing-pitfalls.py)でこの差を確認できる。

ElementTreeの事例も、パッケージ未導入ではない。属性名は名前空間付きで直列化されても、`mc:Ignorable="x14ac xr xr2 xr3"` の属性値中の接頭辞には元の宣言が必要である。合成再現ではXMLパーサーを使うだけでは足りないことを示した。DOMによる修正版は小さな例での回避確認であり、汎用XLSXエディターとして検証済みではない。

保存対照4応答の8ファイルはすべてセル内容に合格し、保持検査には不合格だった。学習院の図形4個・コネクタ4個、法政の図形22個・コネクタ2個、早稲田の拡張入力規則4個・図形2個などの消失を独立に確認した。openpyxlが全Excel要素を読み書きできるわけではないという制約とも一致する。[公式ドキュメント](https://openpyxl.readthedocs.io/en/stable/tutorial.html#loading-from-a-file)

一方、LibreOffice変換後の式属性・幅の小数表現・共有数式の展開などを、全てデータ破壊と呼ぶことも避ける。例えば立命館r1/r3にはSUM式本文と6コメントが残っている。厳密な構造差、実際の機能消失、Excel表示への影響は別の判定である。

### 6 Luna: 編集の手戻りに加え、成果物の返却前に上限へ到達

比較12件中10件が明示的に `max_output_tokens` で終了。上限12,000の追加2件も途中終了した。比較分の出力95,728トークンのうち、提供元のusage上のreasoningは94,948だった。内部の思考内容を分析した数値ではない。

ただし比較12件分のツールログはSolが747,187文字、6 Lunaが749,025文字とほぼ同じで、出力量だけでは差を説明できない。呼出し回数・手戻り・完了までの進め方を別々に測る必要がある。

取得できない11件（比較10件・追加1件）のうち9件では、リモート環境内で `output.xlsx` の保存サイズや再読込結果が出ていた。つまり「作れなかった」と「利用者へ返せなかった」は異なる。未取得の中間ファイルは、合格した成果物に数えられない。

- 立命館r1 #16〜19ではSolと同種のXML正規表現の問題を修正し、最終ファイルは静的合格したが、応答は上限で途中終了した。
- 学習院r3 #19〜20では、結合範囲C28:D28・F28:G28の起点ではないD28/G28へ記入した。XMLの値は確認しても表示される位置を検査せず、応答完了・ファイル取得後に内容不合格となった。
- 早稲田r2 #21は `warnings.catch_warnings(record=True) as w` の `w` をモジュールのように扱い、次の呼出しで `warnings.simplefilter` へ修正した。元の例外ログはなく、生成コードのAPI誤用と修正からの推定である。
- 学習院r1 #19は `get_cell(...) or insert_cell(...)` を使い、子を持たないXML要素を「存在しない」と扱い得る。ログにtruthiness警告が出ており、次の修正は途中終了した。存在判定には `is None` を使う。
- 法政r2は提供元が `completed` を返したが、最終メッセージ・取得可能な成果物がない。上限に近い値でも、明示的な上限終了とは数えず原因未確定とする。

## 改善プロンプトと次の比較方法

[追加指示の候補](../../experiments/llm-export/prompts/avoid-editing-pitfalls.md)は、環境確認、範囲を絞った調査、XML/ZIPの安全な編集、計算キャッシュ、独立検証、成果物返却の6領域を具体化した。大学名・セル番地・正解は含めない。原因分析時点では案の作成までだった。その後、元プロンプトと過去の実験を保持したまま、明示的なCLI選択を実装して比較した。以下は追試前の方針であり、実施条件と結果は[比較結果](llm-prompt-improvement-comparison-2026-10-12.md)を参照する。

次の検証は、まずSolで行う。今回の既知ケースは回帰確認に使い、効果の一般性は未見の入力・書式で別に測る。

| 比較                        | 固定するもの                                          | 変えるもの                                  | 確かめる仮説                                   |
| --------------------------- | ----------------------------------------------------- | ------------------------------------------- | ---------------------------------------------- |
| A: 現行指示                 | Sol、同じ入力、上限8,000、reasoning、評価器、予算条件 | なし                                        | 比較の基準                                     |
| B: 操作上の注意を追加       | Aと同じ                                               | 新候補の指示。原因を分けるなら1領域ずつ追加 | 品質を落とさず手戻り・呼出し・費用を減らせるか |
| C: 検証済み汎用ツールを提供 | Bと同じ                                               | ZIP/XML編集と構造検査を共通関数化           | 指示遵守より実装の固定が必要な領域はどこか     |

Cでも、帳票の解釈・項目の対応・集計はLLMが判断する。大学別変換処理を作る必要はなく、壊しやすいファイル操作だけを固定できる。A/B/Cを一度に混ぜると何が効いたか分からないため、まずA/Bで測り、Cは別実験とする。

評価は「初回の内容・保持・応答完了」「修復後の合格」「手戻りの種類と回数」「ツール呼出し数」「入力・出力・cached/reasoningトークン」「所要時間」「台帳の費用推計」「合格1件あたりの費用」を分ける。Solは既に12/12なので、成功率だけでは改善を捉えにくい。指示が長くなれば入力コストも増えるため、削減額を先に約束しない。過去の静的評価条件は変えず、Excel・表示確認の範囲も明記する。

次回の観測には、例外クラス・メッセージ・短いスタック、外部コマンドの終了コード・stdout/stderr・出力ファイルの有無を残す。モデルが例外を出さない指示に従うだけでは欠落を防げないため、共通の実行ラッパーは別の改善候補となる。生ログは非公開のまま、公開時は提供元ID・パス・機微情報を除外する。`outputs: []` は引き続き実行エラーと別項目で扱う。

## 手元で再現・監査する
