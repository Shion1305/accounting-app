# LLMの帳票編集で起きた失敗と手戻り

調査日: 2026-10-12 / 対象: `initial-evaluation` の保存ログ

初回PoCではSolが12回すべてで静的検査に合格し、応答も完了した。ただし、途中のコードを見ると、XMLの編集、ZIPの書き出し、計算キャッシュの更新を何度かやり直していた。本稿では、成功に至った試行も含めて、どこで作業がつまずいたかを調べた。

5.6 Lunaにはライブラリ不足から復旧した例があったが、その後も記入漏れや書式の破損が残った。6 Lunaは編集の手戻りに加え、出力上限に達してファイルを返せないケースが多かった。失敗の原因は、実行環境だけでなく編集方法や検査の進め方にもあった。

調査には保存済みのログを使い、追加の有料API呼び出しは行っていない。この分析をもとに実施した24応答の追試は、[追加指示の比較結果](llm-prompt-improvement-comparison-2026-10-12.md)にまとめた。

## Solが成功するまでに直したこと

### 正規表現が隣のセルまで取り込む

立命館r1の#6では、セルを探す正規表現を次のように書き換えて再実行していた。

```python
code = In[5].replace('([^>]*)(?:/>|>.*?</c>)', '([^/>]*)(?:/>|>.*?</c>)')
exec(code)
```

元のパターンは自己終了タグ `<c .../>` を通常の開始タグとして扱い、後続セルの `</c>` まで取り込む可能性があった。早稲田r1の#6〜8では、結合セルの左上にあるG5の罫線スタイルが変わったことに気付き、広くマッチしすぎる正規表現を修正した。

学習院r3 #8、立命館r3 #8、早稲田r3 #10にも似た修正があった。直前の出力が空の事例では、実行時にどの例外が出たかは確認できない。

対策としては、名前空間を保てるXML編集処理を使い、行やセルの境界をまたぐ正規表現で置換しないことが考えられる。保存後には、セル番地の行番号と親rowの番号、セル番地の重複、対象外セルの変更を調べる。XMLとして読めるかの確認だけでは、こうした破損を見落とす。

### ZIPの書き出しが元ZIPの読み込みに影響する

学習院r1 #8では、元ZIPを開き直し、書き出しを次の形に直していた。

```python
out.writestr(copy.copy(info), replacements.get(info.filename, z.read(info.filename)))
```

立命館r1 #7、法政r1 #6・r2 #9、早稲田r1 #10・r2 #10・r3 #11、学習院r3 #12にも、元ZIPを開き直すか、メタデータを複製する修正があった。

`ZipInfo` をそのまま別のZIPへの書き込みに使うと、元ZIPを読むためのオフセットがメモリ上で書き換わる。合成ZIPで試すと、オフセットが `[0, 36]` から `[0, 135]` へ変わり、その後の元ZIPの読み込みで `BadZipFile` が出た。`copy.copy(info)` を使うと、元のオフセットは保たれた。

この例外を確認できたのは合成例であり、当時のログに `BadZipFile` が残っていたわけではない。出力したZIPが正常でも、比較用に元ZIPを読む処理が失敗しうることを確かめた。

書き出しにはメタデータのコピーを渡し、検査時は元ファイルを開き直すと、この問題を避けられる。毎回同じ処理が必要なので、共通のZIP書き出し関数にまとめる候補となる。

### 再計算したはずなのに、古い値が残る

| Solの試行       | 最初に観測した値                                        | 修正後の値・操作                                                                     |
| --------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 学習院r1 #5〜11 | 入力C18/C19/C5が各10,000なのに、複数の合計キャッシュが0 | 使い捨てコピーの数式キャッシュを除去し再計算。#8でC17=20,000、C26=30,000、G25=25,000 |
| 法政r2 #6〜7    | E107が旧値3,500                                         | キャッシュ除去・再計算後に9,500                                                      |
| 早稲田r2 #8〜10 | C45=0、G44=-6,700、G45=0、B7も元の表示                  | 再計算後にC45=35,000、G44=28,300、G45=35,000、B7も更新                               |

これらの試行では、LibreOfficeの終了コードを見るだけでは、古い計算値が残ったことに気付けなかった。作業コピーの数式キャッシュを消して再計算し、入力から別途求めた合計と照合する必要があった。結果を最終ファイルへ移す際も、元の数式やパーツを残し、確認できたキャッシュだけを反映する。

一方、立命館r1/r2、早稲田r1、法政r3の4試行ではLibreOfficeを実行していない。モデルが自分で計算して書き込んだキャッシュを `data_only=True` で読み直しても、数式を計算し直したことにはならない。この設定は保存済みの値を読み込むためのものである。[openpyxl公式ドキュメント](https://openpyxl.readthedocs.io/en/stable/tutorial.html#loading-from-a-file)

ローカルのExcelで再計算を確認したのは、Solの各書式r1の4件である。残る試行では同じ確認を行っていない。

### 調査と自己検証にもやり直しがあった

- **説明ファイルを探す処理**: 全12試行が最初に小文字の `skill.md` を読もうとし、保存出力は空だった。立命館r3は一覧を取得した後、大文字の `SKILL.md` を読めていた。ファイル名や大文字・小文字を決めつけた可能性があるが、`FileNotFoundError` のログは残っていない。読む前に存在を確かめる指示が考えられる。
- **大量のログ出力**: 早稲田r1 #2は59,653文字、r2 #5は65,970文字、r3 #4は68,112文字を1回で出力していた。シート構成や機能一覧から必要な場所に絞れば、読み返す量を減らせる可能性がある。ただし図形内の説明や非表示領域も調査は必要であり、費用削減の効果はまだ測っていない。文字数と課金トークン数も一致しない。
- **自分で検査条件を緩める処理**: 学習院r1 #10〜11・r2 #7〜8・r3 #13〜14は、新しいE28/H28の既定書式の表現差を `_style` 比較から除外した。外部の評価器でも合格したが、モデル自身が変更できる検査だけに合否を任せるのは難しい。
- **警告の読み分け**: 12試行中8件でdconfの権限警告が出たが、処理は完了した。早稲田の入力規則の読み込み警告も、元XMLを保った出力から規則が消えたことを示すものではない。法政の元からある参照切れも、新しく壊した数式とは分けて調べた。

## 5.6 Lunaで残った問題

比較12件と追加2件は、すべて応答が完了してファイルを取得できた。比較の静的検査に合格したのは、学習院r1の1件だけだった。

立命館r1 #8と学習院r3 #7には、捕捉した例外を表示した次のログがあった。

```text
ModuleNotFoundError("No module named 'artifact_tool'")
```

環境の説明には `artifact_tool` があることを前提とした指示があったが、実際には読み込めなかった。両試行とも別のライブラリへ切り替えてファイルを作成した。その後にも次の問題が残ったため、ライブラリ不足だけが不合格の原因とは言えない。出力が空だったほかのimport試行については、同じ例外が出たか分からない。

| 試行・操作                                                     | 確認できた失敗                                                           | 改善の焦点                                           |
| -------------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------- |
| 早稲田r1 #9/12、r3 #17/20: 正規表現でセル置換                  | XMLは読めても、r1で47セル・r3で44セルの親行が不正。最初はH6がrow 5に入る | 行・セルの所属検証。正規表現による置換を避ける       |
| 法政r1 #11、r2 #15、r3 #9: openpyxlで保存                      | 金額は合うが、説明用図形22個が全て消失                                   | 元のZIPパーツと図形を比較。通常画像の数だけでは不足  |
| 法政・追加 #11: ElementTreeでシート全体を直列化                | 22図形と内容は保持したが、`mc:Ignorable` が未宣言の接頭辞を参照          | 属性値内にある名前空間接頭辞も保持・検証             |
| 早稲田r2 #20: 団体名をB7へ直接入力                             | 既存VLOOKUP式を消し、必要なE7は未記入                                    | 入力欄と式の結果欄を区別。項目の記入根拠を確認       |
| 早稲田・追加 #25: H2へ日付を補完                               | 別の用途の確認済み日付を転用し、意味が未確定の欄を埋めた                 | 値が存在することと、その欄の値と確認できることを区別 |
| 立命館r2 #14/19、学習院r3 #13                                  | 報告日J1、内訳名B18/B19などが未記入。確認項目にも漏れ                    | 入力事実と出力先の対応・未記入一覧を検査             |
| 法政r1 #14、r3 #12/13、早稲田r1 #15・追加 #27: LibreOffice変換 | 入力と出力が同じパスで保存エラー。別ディレクトリで復旧                   | 終了コード・標準エラー・新規出力を合わせて確認       |

早稲田のセル置換に使われた正規表現は次の形だった。

```python
pat = rf'<c\b([^>]*\br="{re.escape(coord)}"[^>]*)>(.*?)</c>|<c\b([^>]*\br="{re.escape(coord)}"[^>]*)/>'
m = re.search(pat, xml, flags=re.S)
attrs = (m.group(1) or m.group(3)).rstrip('/')
```

最初の選択肢が `<c .../>` にも一致し、後ろのセルの終了タグまで取り込んでいた。`rstrip('/')` で不正な開始タグを直しても、失われた行の境界は戻らない。openpyxlで再読み込みできる状態になった後も、最終ファイルにはセルと親行の不一致が残った。[合成例の再現スクリプト](../../experiments/llm-export/reproduce-editing-pitfalls.py)でこの挙動を確かめられる。

ElementTreeの問題も、ライブラリがなかったためではない。XMLを書き出す際に属性名の名前空間は処理できても、`mc:Ignorable="x14ac xr xr2 xr3"` という属性値に含まれる接頭辞の宣言が失われた。合成例ではDOMを使うことで回避できたが、一般的なXLSX編集ツールとしての検証はまだ行っていない。

対照実験の4応答から作った8ファイルは、すべてセル内容の検査に合格し、保持検査には不合格だった。学習院の図形4個・コネクタ4個、法政の図形22個・コネクタ2個、早稲田の拡張入力規則4個・図形2個などが消えていた。openpyxlがすべてのExcel要素を読み書きできるわけではないという、[公式ドキュメントの制約](https://openpyxl.readthedocs.io/en/stable/tutorial.html#loading-from-a-file)とも一致する。

ただし、変換で生じた差がすべて機能の消失とは限らない。立命館r1/r3にはSUMの式本文と6コメントが残っていた。式の属性、列幅の小数表現、共有数式の展開などは、実際の機能や表示への影響を別途確かめる必要がある。

## 6 Lunaで完了できなかった理由

比較12件中10件は、APIが明示した `max_output_tokens` によって終了した。上限を12,000に増やした追加2件も途中で終わった。比較分の出力95,728トークンのうち、usageに記録されたreasoningは94,948だった。これはAPIの使用量の内訳であり、思考内容を分析したものではない。

比較12件のツールログはSolが747,187文字、6 Lunaが749,025文字で、ほぼ同じ量だった。ログの長さだけでは差を説明できず、呼び出し回数や修正の内容、成果物を返すまでの進め方も調べる必要がある。

ファイルを取得できなかった11件（比較10件・追加1件）のうち9件では、リモート環境で `output.xlsx` の保存サイズや再読み込み結果が出ていた。内部では作成できても、取得できる形で返せなかった可能性がある。中間ファイルの内容は検査できていないため、成功には数えていない。

- **立命館r1 #16〜19**: Solと同じ種類のXML置換の問題を直した。最終ファイルは静的検査に合格したが、応答は上限に達して途中で終わった。
- **学習院r3 #19〜20**: 結合範囲C28:D28・F28:G28の左上ではないD28/G28へ入力した。XMLの値は調べたが、表示される位置は確認していなかった。応答は完了し、ファイルも取得できたが、内容検査には不合格だった。
- **早稲田r2 #21**: `warnings.catch_warnings(record=True) as w` の `w` をモジュールのように使い、次の呼び出しで `warnings.simplefilter` に直していた。元の例外ログはなく、コードの誤用と修正から原因を推定した。
- **学習院r1 #19**: `get_cell(...) or insert_cell(...)` を使い、子を持たないXML要素を存在しないものとして扱う可能性があった。ログにはtruthinessの警告があり、次の修正は途中で終わった。存在確認には `is None` を使う必要がある。
- **法政r2**: APIの状態は `completed` だったが、最終メッセージも取得可能な成果物もなかった。出力は上限に近かったものの、上限終了という通知はなく、原因は未確定である。

## 分析から考えた改善案

[追加指示](../../experiments/llm-export/prompts/avoid-editing-pitfalls.md)では、環境確認、調査範囲、XML・ZIPの編集、計算キャッシュ、検査、成果物の返却という6領域を具体化した。大学名・セル番地・正解は含めていない。

まずSolで現行指示Aと追加指示Bを比べ、その後で必要なら共通ツールCを試す方針を立てた。以下は追試前の案である。A/Bの比較はその後実施し、[別レポート](llm-prompt-improvement-comparison-2026-10-12.md)に結果を記録した。Cは未実施である。

| 比較                        | 固定するもの                                          | 変えるもの                                  | 確かめる仮説                                   |
| --------------------------- | ----------------------------------------------------- | ------------------------------------------- | ---------------------------------------------- |
| A: 現行指示                 | Sol、同じ入力、上限8,000、reasoning、評価器、予算条件 | なし                                        | 比較の基準                                     |
| B: 操作上の注意を追加       | Aと同じ                                               | 新候補の指示。原因を分けるなら1領域ずつ追加 | 品質を落とさず手戻り・呼出し・費用を減らせるか |
| C: 検証済み汎用ツールを提供 | Bと同じ                                               | ZIP/XML編集と構造検査を共通関数化           | 指示遵守より実装の固定が必要な領域はどこか     |

Cでも、帳票の解釈、項目の対応、集計はLLMに任せる。共通化するのは、壊しやすいZIP/XMLの操作と構造検査である。A/Bとの効果を切り分けるため、Cは別の実験とする。

比較では、内容・保持・応答完了の合否に加え、修復後の結果、やり直した処理の種類と回数、ツール呼び出し数、入力・出力・cached/reasoningトークン、所要時間、推計費用、合格1件あたりの費用を記録する。Solはすでに12/12で合格しており、成功率だけでは改善を捉えにくい。検査を省いて速くなった場合も分かるように、再計算やExcelで確認した範囲をそろえて比べる。

既知のケースは以前の結果を壊していないかの確認に使い、新しい入力・書式でも通用するかは別に調べる。追加指示が長くなる分の入力費用もあるため、費用を削減できるかは実測で判断する。

次回は、例外のクラス・メッセージ・短いスタック、外部コマンドの終了コード・stdout/stderr、出力ファイルの有無を記録したい。記録漏れを減らすには、指示に頼るほかに、コードの実行と記録を共通の処理にまとめる案もある。生ログは非公開とし、公開する記録からは提供元ID・パス・機微情報を除く。

## 再現と再集計の手順

合成XML・ZIPを使った3つの再現例と、そのテストは次のコマンドで実行できる。APIキーは不要で、有料APIも呼ばない。元のExcelは変更しない。

```sh
python3 experiments/llm-export/reproduce-editing-pitfalls.py
python3 -m unittest discover -s experiments/llm-export -p 'test_analyze_traces.py'
```
