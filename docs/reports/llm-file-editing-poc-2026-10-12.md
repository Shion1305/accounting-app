# LLMによるExcel帳票編集の検証結果

実施日: 2026-10-12 / 実験ID: `initial-evaluation`

既存のExcel書式と取引データを渡すだけで、LLMが会計報告書を記入できるか検証した。**Solは4大学の基本ケースを各3回、計12回すべてで静的検査に合格し、応答も完了した。** 次はSolを使い、人が確認してから使う下書きの作成を検証する。

今回使ったのは、同じ少量の取引データを繰り返すケースである。新しいデータでの精度や、そのまま提出できる品質までは確認できていない。

接続確認や追加調査を含め、実行したモデル応答は47件。費用の推計は **$2.924513275** で、予算$10に収まった。OpenAIの請求額との照合はまだ行っていない。

[検証計画](../plans/llm-file-editing-evaluation.md) / [費用計測の仕組み](../design/llm-evaluation-gateway.md) / [実行・再検証の手順](../../experiments/llm-export/README.md)

## 実験方法

モデルに渡したのは、既存の参照Excelと合成取引データのJSONである。記入するセルの対応表や大学別の変換コード、採点用の正解は渡さず、費目や記入位置の判断もモデルに任せた。出力したファイルは、モデルとは別の評価プログラムで検査した。

比較対象は `gpt-6.1-sol`、`gpt-6-luna`、`gpt-5.6-luna`。各モデルで4書式を3回ずつ編集し、計36試行を比較した。実行条件は次のとおり。

- Responses APIとCode Interpreterを使用。
- 試行ごとに新しい応答と専用の1GBコンテナを作成。ネットワークは無効。
- reasoningは `medium`、service tierは `default`。
- 出力上限は思考トークンを含めて8,000トークン。
- 試行は順に実行し、自動リトライは行わない。
- 所要時間はアップロード前から静的検査の終了まで。ファイルとコンテナの削除時間は含めない。

このほかに、接続確認を3回、openpyxlで読み込んで保存した際の影響を調べる対照実験を4回、失敗原因を調べる追加実験を4回行った。費用はすべて同じゲートウェイとSQLite台帳に記録した。

参照Excelは、匿名化した研究用のコピーを使った。最新版の正式な提出書式ではない。早稲田では会計報告シートだけを記入し、残る4シートは変更せずに保つ課題とした。法政の元ファイルにある参照切れの数式6セルは、修正対象から外した。

## 評価の基準

結果を読む際は、ファイルの検査とモデル応答の完了を区別する。

- **内容合格**: 金額、分類、残高、識別番号などが合成入力と一致した。
- **静的合格**: 内容に加え、数式、書式、対象外シート、図形、コメント、入力規則、印刷設定などの保持検査に合格した。
- **応答完了かつ静的合格**: 取得したファイルが静的検査に合格し、APIの応答状態と空でない最終回答がともに完了した。
- **Excel確認**: 実際のExcelでファイルを開き、入力変更や再計算を確認した。表示・印刷を確認した範囲は後述する。

静的検査だけでは提出可能かどうかは分からない。現在の評価器は日付の文字列も許容するため、日付がすべてExcelの日付シリアル値になっているとは限らない。最終回答の説明文も、要件をすべて満たしているかまでは自動採点していない。

また、同じ意味のXMLでも表現が変わると差分になる項目がある。不合格になったファイルは生成コードと実ファイルも調べ、数式の破損と、属性や共有数式の表し方の違いを見分けた。

## 評価器の修正

実験中に、評価器が厳しすぎる判定をしていた箇所と、誤りを見逃していた箇所が見つかった。修正前の評価とmanifestを残し、取得済みの全ファイルを同じ修正版で採点し直した。プロンプトや生成ファイルの変更、APIの再呼び出しは行っていない。

### 記入欄の解釈を直した3か所

1. **法政のB101・B104**は固定費目ではなく、記入例の追加費目名だった。使わない例の削除を許可し、初回Solの判定が不合格から合格に変わった。
2. **学習院のC28・F28**は、ラベルと入力値を同じ結合セルに記入できる欄だった。ラベルに正しい団体コード・団体名を加える記入を許可し、初回5.6 Lunaが合格に変わった。任意の文字列の追加やラベルの削除は引き続き不合格とした。
3. **早稲田のH2**は、何の日付を入れる欄か分からず、入力にも該当する日付がなかった。元の `yyyy/mm/dd` または空欄を許可し、Solの3回目が合格に変わった。架空の日付や別の値は認めていない。

### ファイル構造の見落とし

早稲田の初回5.6 Lunaでは、47セルが削除され、さらに残った47セルが異なる行の配下へ移っていた。同じセル番地の重複と、セル番地の行番号が親のrow要素と食い違うファイルを拒否する検査を追加した。総合的な静的合否は変わらなかったが、以後この出力は読み込み時点で不合格とする。値だけを照合した旧判定は、有効な帳票の内容合格には数えない。

学習院の6 Luna・3回目は、表示されないセルへの入力を見逃していた。団体コードと団体名が、結合範囲C28:D28・F28:G28の左上ではないD28・G28に書かれていた。表示されるC28・F28にはラベルしかなかった。

そこで、結合範囲の左上以外に新しい値や数式を入れることを拒否し、その位置の値を内容照合からも除いた。元からある空セルや書式だけのセルは許容する。再評価の結果、この1件だけが静的合格から不合格に変わった。

追加指示を与えた法政の5.6 Lunaでは、ElementTreeによる書き換えで名前空間の宣言が消え、`mc:Ignorable` に未宣言の `x14ac xr xr2 xr3` が残った。各要素で有効な宣言を確認する検査を追加し、この試行を静的不合格へ訂正した。内容の検査結果と、固定条件36試行の合否は変わっていない。

この不備はMicrosoftのOpen XML SDKでも `MC_InvalidIgnorableAttribute` として検出される。[公式の検証テスト](https://github.com/dotnet/Open-XML-SDK/blob/main/test/DocumentFormat.OpenXml.Tests/ofapiTest/McValidationTest.cs#L182-L186)で確認できる。ただし、このファイルをExcelで開いて修復要求が出るかは未確認である。

### 評価結果を読むうえでの注意

評価条件の一部はモデルの出力を見た後で直している。そのため、今回の結果は採点基準を事前に完全固定したベンチマークではない。次の実験では評価器を先に固定する。

プロンプト・入力・元書式のハッシュは各manifestに保存した。初期のランナーは実行時の評価器のハッシュを記録しておらず、`evidence.json` にある実装ハッシュはスナップショット保存時点のものである。

また、6 Lunaの法政2回目はAPI上では `completed` だったが、最終メッセージも取得できる成果物もなかった。出力は7,987トークンで上限8,000に近いものの、APIから上限到達の通知はなく、停止原因は不明として記録した。

## 失敗から分かったこと

5.6 Lunaの法政では、金額は合っていても説明図形が消えていた。早稲田の初回はXML編集でセルが削除・移動し、Excelが修復を要求した。2回目は団体名を参照するB7の数式を上書きし、本来の入力欄E7が空欄だった。合計G45の保存値も28,300で、数式から別途計算した35,000と食い違っていた。

学習院3回目は金額と総計が合っていたが、部費徴収の説明が省かれ、固定費目も変更されていた。早稲田3回目にもセルと親行の不一致やラベルの削除があり、合計の保存値は0のままだった。

一方、学習院2回目は内容の検査に合格したものの、再保存によるXMLや印刷設定の差で静的不合格になった。説明図形を戻す処理は行われており、検出した差分すべてが表示の崩れかどうかは分かっていない。Excelでの確認は自動操作ツールのウィンドウ取得エラーで実施できず、帳票自体のエラーには数えていない。

評価器にも限界がある。すべての数式を実行したり、全セルの保存済み計算値を照合したりはしていない。ファイルの静的検査、Excelでの読み込み、再計算、表示・印刷はそれぞれ確認する必要がある。生成コードの具体的な問題は[失敗・手戻りの分析](llm-file-editing-failure-analysis-2026-10-12.md)にまとめた。

| 固定条件の比較       |     36 |         $2.570155755 |
| 保存ライブラリの対照 |      4 |         $0.184731200 |
| 追加条件             |      4 |         $0.169500520 |
| 接続確認             |      3 |         $0.000125800 |
| 合計                 |     47 |     **$2.924513275** |

内訳はトークン料金 **$1.604513275** と、専用コンテナ44個の **$1.320000000**。事前の試算約$3〜$6の下限付近で、予算$10に対する残額は **$7.075486725** だった。台帳では整数のnanoUSDを使い、丸める前の値をCSVとJSONに保存した。

料金は、APIが返した入力・キャッシュ読込・キャッシュ書込・出力の使用量に、実行日の単価を掛けて求めた。思考トークンは出力の内訳なので重複して足していない。コンテナは専用1GBを1個あたり$0.03で計算し、内部のツール呼び出し回数には掛けていない。途中終了した試行も計上した。

別実装による料金監査の4,003項目がすべて通り、47応答の使用量と44コンテナから再計算した額が台帳と一致した。311件の通信記録を照合し、44コンテナとアップロード84ファイルの削除も確認した。費用が未確定の呼び出しと、未精算の予約は0件だった。

試行別CSVは45行で、内訳は比較36件、対照5件、追加4件である。対照には識別子の検査で送信前に止まった1件を含む。この1件はAPI呼び出し0・費用0として記録し、接続確認3件は台帳と集計にだけ含めたため、CSVの行数と応答数は一致しない。

以上は使用量に基づく推計であり、OpenAIの確定請求額ではない。税・為替・確認作業の人件費・本番運用費は含まない。後日請求データを取得した際は、この推計との差額を確認する。

## 実装と記録の検証

初回スナップショットの保存時にはNodeの41テスト、Pythonの39テスト、TypeScriptのstrict型チェックが通った。4参照ファイルのハッシュは変わっておらず、比較・追加実験40試行で取得した29成果物のハッシュと評価記録も一致した。料金監査は[監査スクリプト](../../experiments/llm-export/audit-billing.py)で再実行できる。

PRの準備時には、費用不明の応答を台帳へ書き込めない場合に新たな送信を止める処理を補強した。評価器では、指数表記のセル参照への誤認、不正な文字列セル、対照実験の名前空間接頭辞の検査を修正した。この時点でNodeの44テストとPythonの42テストが通り、実APIを呼ばないCIも追加した。

修正後の評価器で、比較26成果物、追加3成果物、対照4件の8ファイルを再検証した。既存の合否は変わらず、追加した名前空間検査8件も通った。入力・成果物・manifest・評価記録の計133ファイルのハッシュが不変であることも確認した。成果物がなかった試行は再実行していない。

## 今回の範囲と次の検証

**次はSolを使った下書き作成を検証する。** 大学別のセル対応表を渡さずに基本ケースを編集できたため、人が確認して使う用途の候補とする。

未検証なのは、取引0件、明細枠の超過、長文、大量明細、不足・矛盾情報、帳票内の悪意ある指示、現在のDBだけを使った入力、正式な提出書式、アプリとの接続である。同じ4ケースの反復から、本番の成功率やp95は推定できない。

次の実験では評価器を先に固定し、実験に使っていない取引や境界条件を追加する。対象ファイルはExcelでの再計算・表示・印刷まで確認する。安価なモデルについては、自由にXMLを編集させる方法と、結合セルやZIPパーツを安全に扱う共通ツールを渡す方法を比べる。共通ツールにも大学別の判断や正解は組み込まない。

途中終了した試行の一部では、ログに `output.xlsx` の保存があってもContainers Files APIから取得できなかった。こうした中間ファイルの内容は検査できていない。取得できなかったことだけで、内部でもファイルを作れなかったとは判断していない。

調査、評価器の修正、目視確認にかかった作業時間は測定していないため、今回のAPI費用から運用全体の安さは判断できない。DB取得、出力API、利用者画面、自動提出への組み込みも未実装である。

その後、Solの手戻りを分析して追加指示を比較した。24応答の追試とその費用は、[追加指示の比較結果](llm-prompt-improvement-comparison-2026-10-12.md)に記録し、本稿の47応答には含めていない。
