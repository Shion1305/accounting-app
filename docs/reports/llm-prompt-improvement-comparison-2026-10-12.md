# Solへの追加指示の比較結果

実施日: 2026-10-12 / 対象: `gpt-6.1-sol`

初回実験で見つかった手戻りを減らすため、XMLやZIPの編集方法、再計算、保存後の検査について指示を追加し、元のプロンプトと比較した。

**追加指示の標準採用は見送る。** ツール呼び出しは約29%減ったが、応答が完了して静的検査にも合格した試行は、現行版の12/12に対して追加版は9/12だった。時間の中央値は約34%、合格・完了1件あたりの費用は約39%増えた。

追加版は実験用の選択肢として残し、標準プロンプトは現行版のままにする。今回の24応答の費用は推計 **$3.3532108**、初回PoCを含めた累計は **$6.277724075** だった。

[比較計画](../plans/llm-prompt-improvement-comparison.md) / [初回PoC](llm-file-editing-poc-2026-10-12.md) / [手戻りの原因分析](llm-file-editing-failure-analysis-2026-10-12.md)

## 比較した条件

Aは初回PoCと同じプロンプト、BはAの末尾に[追加指示](../../experiments/llm-export/prompts/avoid-editing-pitfalls.md)を加えたものである。追加したのは、環境の確認、調べる範囲の絞り込み、XML・ZIPの編集、計算キャッシュの扱い、保存後の検査、成果物の返却に関する指示。大学名・セル番地・正解は含めていない。

同じ4書式と合成JSONを使い、各条件で3回ずつ、計24回試した。出力上限8,000トークン、reasoning medium、default tier、ネットワーク無効の1GB Code Interpreterコンテナ、評価器、採点用の正解をそろえた。

同じ書式・同じ反復番号のA/Bを1組として順に実行し、Aを先にする組とBを先にする組を6組ずつ用意した。試行ごとに新しい応答とコンテナを作り、途中の指示・上限変更や、失敗した試行だけのやり直しは行っていない。

最初の8応答を監査してから、残り16応答へ進んだ。実行前に固定した18ファイルのハッシュを送信前と最終監査で確認した。初回PoCの47応答と保存済みの結果には手を加えていない。

## 減らせた手戻り

全24応答のコードとログを追うと、編集や検査のためにコードを書き直した跡があったのは **Aが11/12、Bが7/12** だった。ここで数えたのは修正があった試行であり、例外の数や修正に成功した回数ではない。

Bの7件には、上限までに解決しなかった学習院r1・r3の2件も含む。また、Bの3試行は途中で終わっているため、最後まで進めた場合の修正回数は分からない。件数が少ないことだけで、品質が上がったとは判断できない。

環境確認コードの構文修正はA/Bに各1件あった。任意の説明ファイルを読もうとしてやり直した試行はAが12件、Bが0件だった。これらは編集・検査の手戻りとは別に集計した。元の例外ログがないものはコードの変化からの推定として記録し、空の出力やツール呼び出しを例外として数えてはいない。

### 早稲田r1: セルの欠落を防げた

Aではセルを書き換える正規表現が隣のセルまで取り込み、XML内のセル数が349から184へ減った。13回目のツール呼び出しで165セルの欠落に気付き、14回目で元ファイルから作り直し、15回目で全349セルの保持と再計算を確認した。

Bは最初からXMLの構造を使って編集し、ZIPのメタデータを複製して保存したため、このやり直しがなかった。ツール呼び出しは15回から5回、時間は134.003秒から88.138秒へ減り、A/Bともファイルは静的検査に合格した。

### 立命館r2: 呼び出しは減ったが、時間と費用は増えた

Aは正規表現の作り直し、元ZIPの開き直し、古い計算キャッシュへの対処が必要だった。BはXML・ZIPを最初から安全に扱い、作業コピーのキャッシュを消して再計算できたため、同じやり直しはなかった。

ただし、時間は74.883秒から76.093秒、費用は$0.1020331から$0.1165587へ増えた。呼び出し回数の削減が、そのまま高速化や節約につながるわけではなかった。

## 追加指示で増えた作業と失敗

### 学習院は書式の検査中に上限へ達した

学習院では、Aは3回とも8,000トークン以内で完了したが、Bは3回とも上限に達した。Bは金額やファイルの作成後も、新しく作ったセルと、元XMLに存在しなかった空セルの書式を比較し続けていた。

| Bの試行 | 終了までに確認できたこと                                                                                  | 結果                                                 |
| ------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| r1      | 再計算・数値照合後、新規セルE28/H28の既定書式を調査。誤った行書式の仮定を修正する検証コードが途中で切れた | 成果物を取得できず、静的合格とは扱わない             |
| r2      | 元XMLと新しく開いたブックで、スタイルの表現差・存在しないセルの扱いを確認し、検証を終えた                 | ファイルは取得・静的合格。最終説明が途中終了         |
| r3      | 最終ファイルを保存して数値を確認した後、既定書式・列書式の扱いを調査。修正案のコードが途中で切れた        | ファイルは取得・静的合格。最後の修正・検証案は未実行 |

r3では、ライブラリ上の書式オブジェクトを比べると多くの差が出たが、属性を表示すると同じ値の項目もあった。配置属性には差があり、列から引き継ぐ書式との関係を含め、実際のExcelでの表示は確認できていない。静的検査には合格しているものの、検出した差分が見た目にどう影響するかは未確認である。

Aの学習院r3も同じ種類の差を調べた。列書式の読み出し先を直し、E28/H28に既存の列書式を明示して完了した。Bのr3は、その修正案を含むコードが途中で切れており、取得したファイルには適用されていなかった。

ログ内の `AssertionError` という記述の一部は、モデルが診断として出力した文章だった。Pythonの例外トレースとは分けて記録している。

### 検査用に生成したコードにも誤りがあった

- **LibreOfficeの起動設定**: 立命館r1と早稲田r3のBでは、GUI用の設定を渡していた。終了コードは0でもX11の表示エラーが出て、ファイルは作られなかった。ヘッドレス用の設定に直すと成功した。
- **変更不要セルの判定**: 法政r2のBは、書き込み予定の全セルにXML差分が出るはずだと検査した。しかしD7は元から期待値で、書き換える必要がなかった。検査を修正して完了した。
- **名前空間の比較対象**: 立命館r3のBは、参照属性を持たないXML要素まで比較に含め、正当な値要素の追加を差分と判定した。参照属性のある要素に絞って比較し直した。

法政r2には、常に真になる元ファイルのハッシュ検査もあった。元ファイルが変わっていないことは、このコードではなく、ローカルの別の検査で確認した。

法政r3ではA/Bとも最初の環境確認コードにインデントの誤りがあり、2回目の呼び出しで修正した。保存コードを実行せず `ast.parse` に渡すと、Aの5行目とBの12行目で `IndentationError: unexpected indent` を再現でき、修正後は構文解析に通った。ただしAPIの保存出力は空で、実行時の例外トレースは残っていない。

いずれも依存ライブラリの不足ではなく、生成したコードや設定の問題だった。モデルが「検証した」と説明していても、検査コードと実行結果を確かめ、合否は外部の評価器で判定する必要がある。

## 検査した範囲の違い

Bの時間が増えた理由には、検査範囲が広がったこともある。法政r1では、Aは生成した計算コードで表示対象の22数式を確認した。BはLibreOfficeも使い、元からエラーがある6セルを含む92数式を確認した。この追加作業まで無駄な反復とは言えない。

一方で、モデルの説明が確認できた範囲を超えている例もあった。早稲田r1のBは全数式を再計算したと説明したが、直接確認できたのは対象の4数式だった。対象外の領収書シートは元のキャッシュを保っていたため、説明どおりにすべてを再計算したとは記録していない。

今回の追加比較では、ローカルのExcelによる再計算、修復警告、表示、PDFの確認は行っていない。Code Interpreter内のLibreOfficeでの確認までが対象であり、初回PoCでのExcel確認結果を新しいファイルに引き継ぐことはできない。

## 費用の確認と再検証

2つの台帳を、ゲートウェイとは別の計算処理で照合した。24応答のトークン料金$2.6332108と、24個の1GBコンテナ料金$0.72を合わせた推計は **$3.3532108** だった。各条件の予算$3.50以内で終了し、費用が未確定の呼び出しは0件だった。アップロードしたファイルとコンテナの削除記録も確認した。

計算に使った単価は100万トークンあたり入力$2、cached入力$0.10、cache write $2.50、出力$10。コンテナは1個あたり最初の20分相当として$0.03を計上し、各コンテナの寿命もその範囲内だった。実行前に[公式料金表](https://developers.openai.com/api/docs/pricing)と照合した単価であり、確定請求額との照合はまだ行っていない。

監査では加工前のusage、リクエスト設定、台帳、レポート、CSV、入出力のハッシュ、評価結果、削除記録を突き合わせた。重複計上、未確定費用、固定したファイルの変更、予定した実行順からの逸脱は見つからず、集計の `auditStatus` は `pass` だった。

`pnpm check:llm-export` ではTypeScript 51件とPython 68件の計119テスト、strict型チェック、4参照Excelの構造検査が通った。モック応答と合成データで検証するため、実APIは呼ばない。

## 次に検証すること

今回の追加指示をそのまま標準設定には採用しない。XML・ZIPの編集やキャッシュの扱いは改善した例があったものの、同じ出力上限で作業を終えられないケースが増えた。上限を増やせば解消するかは、まだ試していない。

次の候補は、追加指示を絞ることと、書式比較やヘッドレス再計算を検証済みの共通関数にまとめることである。帳票の解釈や記入位置の判断はLLMに任せつつ、繰り返し間違えたファイル操作や検査処理をコードで支える。この案の効果は今後の実験で確かめる。

今回も既知の4書式と少量の同じ入力を3回ずつ使った。新しい書式への効果や、追加した指示のうちどれが効いたかは分からない。キャッシュや実行環境の変動もあるため、この結果だけで安定した改善率は示せない。

## 記録の保存先と再集計

詳細記録は `experiments/llm-export/artifacts/diagnostics/sol-prompt-comparison-2026-10-12/` に保存している。`plan.json` は実行前に固定した条件・ハッシュ・順序、`first-eight.json` は最初の8応答の監査、`comparison.json` は全24応答の集計、`recovery-review.json` は試行ごとの修正と確認範囲の記録である。

このディレクトリはGit管理外のため、再集計にはローカルの元ログと台帳が必要になる。次のコマンドはAPIを呼ばない。保存済みの結果を残すため、出力先にはまだ存在しないファイル名を指定する。

```sh
node experiments/llm-export/report.ts --experiment sol-prompt-baseline-2026-10-12
node experiments/llm-export/report.ts --experiment sol-prompt-improved-2026-10-12
python3 experiments/llm-export/compare-prompts.py --repeats 3 --output experiments/llm-export/artifacts/diagnostics/sol-prompt-comparison-2026-10-12/comparison.rechecked.json
pnpm check:llm-export
```

公開するMarkdownには比較条件、集計結果、判断の根拠を記録する。APIキー、生の要求・応答、提供元ID、ローカル絶対パスは含めない。
