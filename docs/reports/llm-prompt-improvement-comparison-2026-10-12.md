# Solの追加指示は実際に改善したか

実施日: 2026-10-12。対象は `gpt-6.1-sol`。初回PoCと原因分析に続く、現行指示Aと追加指示Bの比較。

**XML・ZIPなどの手戻りは減ったが、追加指示をそのまま採用できる改善にはならなかった。** 24応答を実行した結果、応答完了かつ静的合格は現行版の12/12に対し、追加指示版は9/12。ツール呼出しは約29%減ったが、時間の中央値は約34%増え、合格・完了1件あたりの費用は約39%増えた。追加指示版は明示的に選ぶ実験条件として残し、標準のプロンプトは現行版を維持する。

今回の追加費用推計は **$3.3532108**。初回PoCを含む累計は **$6.277724075**。どちらもusageとコンテナ数からの推計であり、提供元の確定請求額ではない。

## 何を変更して比較したか

Aは初回PoCとバイト単位で同じプロンプト。Bは[原因分析から作成した追加指示](../../experiments/llm-export/prompts/avoid-editing-pitfalls.md)の本文を末尾へ加えた。環境確認、調査範囲、XML・ZIPの安全な編集、計算キャッシュ、保存後の検証、成果物の返却を具体化している。大学名・セル番地・正解は追加していない。

同じ4書式・合成JSONについて、各条件を3回ずつ実行した。出力上限8,000、reasoning medium、default tier、ネットワーク無効の1GB Code Interpreterコンテナ、独立評価器・正解を固定した。A/Bを同じ書式・反復の組として直列実行し、A先行とB先行を各6組にした。すべて新規応答・コンテナで、途中の指示変更、上限変更、選択的な再試行はない。

最初の8応答の監査後に残り16応答へ進んだ。実行前に固定した18ファイルのハッシュを送信前と最終監査で確認した。初回の47応答と凍結済み結果は変更していない。

## 実際に減った手戻り

ここでいう手戻りは、保存されたコード・ログから確認した編集・検証の修正系列である。空出力やツール呼出し数を例外件数とみなさない。例外ログがない事例は、前後のコード変更からの推定と明記する。環境確認のコードや任意の説明ファイルを探す処理は、編集・検証の集計から分ける。

全24応答を目視で追跡すると、編集・検証の修正系列が残っていた試行は **Aが11/12、Bが7/12**。Bの7件には上限までに解決できなかった学習院r1・r3の2件を含む。これは実際の例外の全件数や修正成功数ではない。Bの3試行は途中終了しているため、その先で起こり得た修正も観測できず、件数の少なさだけを品質改善の証拠にしない。別枠の環境確認コードの構文修正は各1件、任意の説明ファイルの読出しからの立て直しはAが12件、Bが0件だった。観測された値・コードからの推定・未実行の修正案を[試行別記録](../../experiments/llm-export/diagnostics/sol-prompt-comparison-2026-10-12/recovery-review.json)で区別している。

早稲田r1のAでは、セルを書き換える正規表現が隣のセルまで取り込み、XML内のセル数が349から184へ減っていた。#13で165セルの欠落を確認し、#14で元ファイルから作り直し、#15で全349セルの保持と再計算を確認した。Bでは最初からXMLを構造として編集し、複製したZIPメタデータで保存したため、この修正は発生しなかった。ツール呼出しは15回から5回、時間は134.003秒から88.138秒へ減り、どちらの成果物も静的合格した。

立命館r2でも、Aは正規表現の作り直し、元ZIPの開き直し、古い計算キャッシュへの対処を経た。Bは最初からXML・ZIPを安全に扱い、作業コピーでキャッシュを消して再計算し、修正系列なしで合格した。ただし、時間は74.883秒から76.093秒、費用は$0.1020331から$0.1165587となった。呼出し回数が少ないことだけで高速化・節約とは判断できない。

## 新たな負荷・失敗も増えた

### 学習院: 編集後の書式検証で上限に到達

Bの学習院は3回とも出力上限に達した。同じ8,000トークン条件で、Aの学習院は3回とも完了した。Bでは数値やファイルの作成後も、新しく明示的に作ったセルと元から暗黙に空だったセルの書式比較を続けていた。

| Bの試行 | 終了までに確認できたこと                                                                                  | 結果                                                 |
| ------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| r1      | 再計算・数値照合後、新規セルE28/H28の既定書式を調査。誤った行書式の仮定を修正する検証コードが途中で切れた | 成果物を取得できず、静的合格とは扱わない             |
| r2      | 元XMLと新しく開いたブックで、スタイルの表現差・存在しないセルの扱いを確認し、検証を終えた                 | ファイルは取得・静的合格。最終説明が途中終了         |
| r3      | 最終ファイルを保存して数値を確認した後、既定書式・列書式の扱いを調査。修正案のコードが途中で切れた        | ファイルは取得・静的合格。最後の修正・検証案は未実行 |

r3では、ライブラリ上の書式オブジェクト比較が多数の差を報告した一方、出力した属性表現が同じ項目もあった。配置属性には差があり、列から継承する書式との関係はネイティブ表示で未確認である。したがって、すべてを見た目の破損とも、すべてを無害な表現差とも断定しない。静的評価の合格は、この表示上の不確実性を解消しない。

Aの学習院r3も同種の差を調べたが、列書式の読出し先を直し、E28/H28へ既存の列書式を明示して完了した。Bのr3ではその案を含むコードが切れ、取得ファイルには適用されていない。この差は静的合否だけでは見えなかった。

保存ログ中の `AssertionError` という説明の一部はモデルが診断として出力した文章であり、Pythonが出した例外トレースではない。実際の比較結果・コード・取得ファイルと区別して記録した。

### 追加した検査自身にも誤りがあった

- 立命館r1・早稲田r3のBは、LibreOfficeへGUI用の設定を渡し、終了コード0でもX11表示エラー・出力ファイルなしになった。ヘッドレス用の設定へ直して成功した。ライブラリの不足ではなく、生成した起動設定の問題だった。
- 法政r2のBは「書込み予定の全セルでXML差分が出るはず」と検査したが、D7は元から期待値だった。変更不要のセルを認識して検査を修正した。同じ処理には常に真になる元ファイルのハッシュ検査もあり、その検査自体は不変性の証拠にならない。元ファイルの不変性はローカルの独立検査で確認した。
- 立命館r3のBは、名前空間参照の検査で属性を持たないXML要素まで一覧化したため、正当な値要素の追加を差分として検出した。実際に参照属性を持つ要素だけを比較するよう修正して完了した。

法政r3ではA/B双方の最初の環境確認コードにインデント不備があり、2回目の呼出しで取り除いた。保存コードをローカルで実行せず `ast.parse` に渡すと、Aの5行目・Bの12行目で `IndentationError: unexpected indent` を再現し、修正後は構文解析に成功した。これは編集前のコード生成の問題で、依存ライブラリ不足ではない。保存出力が空なので、API実行時の例外トレースが記録された事例とは区別する。

モデルが「検証した」と返しても、実際の検査コード・実行結果・外部評価が必要である。自己検証だけを合否の正本にはしない。

## 検証範囲の変化

Bは一部の試行で、Aより広い範囲の数式を確認した。法政r1では、Aは生成した計算コードで表示対象22数式を確認したのに対し、BはLibreOfficeと生成コードを併用し、元からあるエラー6セルを含めて92数式を確認した。この負荷は単なる無駄な反復とは区別する。

一方、モデルの最終説明が検証範囲を広く言いすぎる場合もあった。早稲田r1のBは全数式の再計算を説明したが、直接確認できるのは対象の4数式であり、対象外の領収書シートのキャッシュは保持されていた。モデルの説明文をそのまま検証済み範囲へ採用していない。

今回は新たなローカルExcel確認、修復警告、PDF・見た目の検査を行っていない。Code Interpreter内のLibreOffice確認とローカルExcelでの確認は別であり、初回PoCのExcel確認を今回の成果物へ引き継がない。

## 費用の照合と再検証

新しい2台帳を独立に照合した。24応答・24個の1GBコンテナの推計は、トークン料金$2.6332108とコンテナ料金$0.72の合計 **$3.3532108**。各条件$3.50の送信予算内で終了し、未解決費用は0件、アップロード・コンテナの削除記録を確認した。各コンテナの寿命は初回20分の推計範囲内だった。

登録単価は100万トークンあたり入力$2、cached入力$0.10、cache write $2.50、出力$10。1GBコンテナは初回20分相当$0.03で推計した。実行前に[公式料金表](https://developers.openai.com/api/docs/pricing)と照合したが、提供元の請求集計との突合は行っていない。送信予算も提供元の請求額を保証する上限ではない。

監査はローカルゲートウェイと別の実装でnanoUSD単位から再計算した。raw usage・要求設定・台帳・レポート・CSV・入力と出力のハッシュ・独立評価・削除記録を照合し、各応答とコンテナの重複、未解決費用、凍結ファイルの変更、実行順の逸脱がないことを検査した。公開集計の `auditStatus` は `pass`。元の履歴を書き換えて合否を合わせる処理はしていない。

## 次の判断

追加指示全文を標準設定へ採用するのは見送る。XML・ZIPの安全な書出しや計算キャッシュの扱いには具体的な改善例があるが、同じ出力枠で必要な作業を終えるという条件を満たせなかった。出力上限を増やせば解消するかは今回検証していない。

次に検証するなら、追加指示を絞り、既定書式・継承書式・変更不要セルの比較やヘッドレス再計算を、単独で検証した汎用ヘルパーにまとめる案がある。帳票の意味の解釈・記入位置の判断はLLMへ任せたまま、繰り返し発生した実装上の誤りと、自己検証が終わらない問題を減らす。成果物を取得した時点の独立検査と、説明文の完了状態も引き続き別に記録する。この次案の効果は未検証であり、今回の結果には含めない。

既知の4書式・小さな同一入力を3回ずつ繰り返した比較なので、未見書式への効果は分からない。複数の指示を同時に追加しており、1文ずつの寄与も切り分けていない。入力キャッシュ量と実行環境の変動もあるため、この標本から統計的な改善率や再現保証は主張しない。
