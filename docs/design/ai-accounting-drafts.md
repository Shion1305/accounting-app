# AIによる会計書類の下書き作成

更新日: 2026-11-08

大学の書式をアップロードし、登録済みの会計データをAIに渡して、記入できる部分を埋めたファイルを受け取る。アップロードはPDF、Office文書、CSVに限定し、拡張子は `.pdf`、`.xlsx`、`.doc`、`.docx`、`.pptx`、`.csv` を受け付ける。画像、アーカイブ、プログラムなどは対象外。対応形式はAPIの `capabilities` から画面に表示する。

## 利用の流れ

`/dashboard/accounting-export` で書式1ファイル（10MB以下）、対象期間、任意の依頼内容を指定する。期間を空にすると全期間になる。日付の境界は日本時間の開始日0時から終了日の翌日0時まで。

不足している情報の入力は求めない。費目、用途、開始残高、購入日など、保存されていない事実は作らず、記入できなかった箇所をAIの説明に残す。利用者は生成ファイルを取得して使う。会話での追加編集や取引登録画面の拡張は今回の対象外。

生成完了は、モデルの処理が完了してファイルが返されたことを表す。大学別の採点、数式の再計算、画面・印刷の検査は本体では行わない。出力上限などで処理が途中終了しても取得できるファイルがあれば、途中終了と表示して返す。ファイルがなければ生成失敗とし、AIの説明があれば表示する。

## データと生成処理

実装は `apps/server/src/accounting/` に分ける。

- `storage.ts`: 所属サークルの収入・支出・団体情報を取得し、実行記録をD1で管理する。
- `service.ts`: 作成、状態取得、成果物の取得、終了、期限切れ清掃を担当する。
- `provider.ts`: OpenAIへのファイル送信、Responses API、Code Interpreter、ファイル取得・削除を担当する。

支出は `expense_records` を使う。承認時に反映済みの立替を、申請レコードからもう一度足さない。関連する申請の件名・メモ・支払者名は補助情報として添える。立替由来の支出日は現在の実装では申請日なので、その意味もJSONへ明記する。領収書画像や認証情報は渡さない。

書式と `accounting-data.json` をアップロードし、Responses APIを `background: true`、`store: true` で呼ぶ。標準モデルはPoCで採用した `gpt-6.1-sol`。reasoningはmedium、出力上限8,000トークン、試行専用の1GBコンテナ、ネットワーク無効とする。プロンプトは現行指示を基に、既存データだけで可能な箇所を埋める依頼にしている。実験の追加指示版は採用しない。

モデルのファイル引用から生成ファイルを取り出す。ファイル名や形式はExcelに固定しない。拡張子やサイズの確認は送受信の制約のためであり、帳票内容の合否判定ではない。会計JSONも10MBを超える場合は期間を絞るよう求め、黙って取引を省かない。

## APIとアクセス制御

すべて既存の管理者認証・サークル所属確認の下に置く。サークルIDと実行者は認証から決め、リクエスト本文では受け付けない。

| API | 用途 |
| --- | --- |
| GET `/api/admin/accounting/capabilities` | 利用可否、上限サイズ、対応拡張子 |
| POST `/api/admin/accounting/exports` | multipartの `template`、`requestId`、任意の `from`・`to`・`instructions` で生成開始。202を返す |
| GET `/api/admin/accounting/exports/:id` | 状態、AIの説明、取得できるファイルを返す |
| GET `/api/admin/accounting/exports/:id/files/:fileId` | 登録された成果物をattachmentとして中継する |
| DELETE `/api/admin/accounting/exports/:id` | 生成を終了し、一時リソースを削除する |

`requestId` はブラウザーで作るUUID。同じIDでPOSTを再送しても、新しい有料応答を作らない。生成リクエストを自動で再送しない。ファイル取得でも実行の所属を確認し、その実行で登録した成果物IDだけを受け付ける。APIキーや提供元のファイルIDはブラウザーに返さない。

画面は3秒ごとに状態を取得する。通信エラー時は自動取得を止め、「状態を確認」から再取得できる。実行IDを画面URLに残すため、再読み込み後も同じ実行を確認できる。新しく作成する操作では、前の生成を終了して別のIDを使う。

## 実行記録と一時ファイル

D1の `accounting_exports` に実行者、サークル、期間、モデル、日時、状態、使用量と一時リソースの情報を保存する。取引JSONとファイル本体は保存しない。AIの説明と取得用IDは実行中の表示に使い、清掃後は消す。使用量の記録は確定請求額を意味しない。

状態は `starting` → `processing` → `finalizing` → `generated` / `incomplete` / `failed`。終了操作は `closed`、期限切れは `expired`。条件付き更新で、同時の状態取得が終了済みの実行を再び有効にしないようにする。

入力のアップロードには1時間の有効期限を付ける。処理終了後にも入力ファイルを削除する。生成ファイルは提供元に一時保持し、APIで中継する。アプリのR2には保存せず、履歴一覧や過去ファイルの再ダウンロード機能も作らない。

受け取り期限は処理終了から最大1時間。提供元のコンテナが先に失効すれば、その時点で取得できなくなる。生成の開始後1時間たっても完了が確認できない実行も期限切れとする。

終了時に進行中の応答を取り消し、入力ファイル、コンテナ、応答を削除する。毎時のscheduledハンドラーでも、期限切れと削除失敗を最大50件ずつ再処理する。削除に失敗したIDは再試行できるよう残す。アプリの取引・画像は削除しない。

## 設定と確認

- ローカルは `apps/server/.dev.vars`、本番はWorkerのsecretに `OPENAI_API_KEY` を設定する。未設定でも既存機能は動き、生成画面には利用不可と表示する。
- `ACCOUNTING_MODEL` は `wrangler.jsonc` で設定する。
- 既存DBには `apps/server/drizzle/0005_unusual_junta.sql` だけを追加適用する。空のDBでは従来どおり全マイグレーションを順に適用する。
- `pnpm --filter server test` はSQLiteとモックAPIで権限、取引抽出、複数形式、部分結果、再送、清掃を検証する。実APIは呼ばない。

実際のAPI接続と大学書式での生成は、APIキーを設定した環境で確認する。本番デプロイと実DBへのマイグレーション適用は、コード変更とは別に行う。
