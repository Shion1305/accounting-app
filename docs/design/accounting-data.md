# 会計データの保存・入力・ライフサイクル

更新日: 2026-09-27

位置付け: 設計方針。未実装の契約・API・保存方式は提案として記載する。

[ドキュメント一覧](../README.md)

## 会計項目マスタと分類

会計項目マスタに `id`、`circleId`、`code`、`name`、`kind`、`sortOrder`、`isActive` を持たせる。表示名ではなくIDで取引から参照し、大学別マッピングには安定したcodeを使う。

`circleId + kind + code` の一意性を保証する。既存サークルへの初期登録、新規サークル作成時の登録、再試行時の重複防止を実装する。

支出項目は消耗品費・備品費・食費・交通費・印刷費・通信費・雑費を基準に、正式テンプレートの粒度へ調整する。収入項目は会費・補助金・寄付金・その他収入を案とし、収入書式で確認する。繰越金は当年度収入と二重計上しないよう開始残高として分ける。

収入・支出・立替申請へcategoryIdを追加する。新規登録では選択必須とし、APIで所属サークル・収支区分・有効状態を検証する。既存行はNULLを許容して未分類とし、一覧から分類を補完する。未分類を自動的に雑費へ変更しない。

過去取引を壊す物理削除は避け、将来の項目廃止はisActiveで管理できるようにする。

## 購入日・備考・大学固有情報

- 立替に購入日を追加し、承認時に支出へ引き継ぐ。申請日時と分ける。
- 既存立替の実購入日は申請日時から確定できない。従来の日付を暫定値として残す場合も確認済みと区別し、購入日を必要とする提出出力の前に補完する。
- 摘要と備考、立替の短い件名と長いメモを分離する。
- 法政の用途と、領収書の提出区分（決算書・活動規模・正課外・活動実態）および番号対応を扱う。提出履歴はファイルのエクスポート履歴とは分ける。
- 法政の対象金額・対象外金額・備考は提供ファイルでは非表示である。誰が何の制度について入力するかを確認してから必須性を決める。費目から対象額を推定しない。
- 対象額を二分する運用が確認できた場合は `対象外金額 = 金額 - 対象金額` とし、0以上かつ総額以下を検証する。未確認はNULLとし、確定した0円と区別する。
- 大学固有情報は型と検証ルールを持つフィールドとして管理する。未検証の汎用JSONだけで扱わない。
- 保存先は取引の事実、領収書・申請の関係、年度・帳票プロフィール、制度別の判定に分ける。全大学の項目を一つの取引行に追加しない。具体的な根拠と構成案は[大学別調査](../universities/README.md)と本書の保存単位を参照する。
- 立替由来の支出の分類補完は可能にするが、金額や出所を任意に変更する機能には拡張しない。

## 承認・期間・残高

提出用の標準対象は、手動登録の収支と、承認済み・精算済み立替から作成された支出とする。立替申請と支出を両方加算せず、承認の再試行・競合でも二重計上しない。精算済みへの変更で支出は増やさない。

「全データ」の意味は現在の承認モデルに合わせて確定する。推奨は、未承認を含む確認用モードを提出用と区別すること。却下申請を提出用支出へ含めない。

- 年度・月・任意期間・全期間を共通の選択条件へ正規化する。
- 年度開始月は設定可能にする。4月を初期値案とし、大学書式で確認する。
- 月・任意・全期間でも、帳票の提出年度を明示する。
- 日付境界は日本時間。開始日を含み、終了日の翌日を含まない範囲にする。
- 同日取引も順序が安定するよう、取引日・登録日時・識別子で並び順を確定する。
- 開始残高は年度・基準日とともに明示的に保存する。履歴が不完全な状態で0円と推定しない。
- 月・任意期間の開始残高は、確認済み基準残高と期間開始前までの収支から計算する。根拠不足なら補完を求める。
- 期末残高は `開始残高 + 期間内収入 - 期間内支出`。帳票上の繰越金と実際の支出を区別する。

現行の新規金額入力は正の整数。負数の表示形式は保持するが、負額登録による返金・訂正という新しい業務は別途決める。

## 現行実装との照合

調査基準は `dev` の `ed644e6`。`packages/accounting-export` と変換テストの行は、未マージの[PR #2](https://github.com/Shion1305/accounting-app/pull/2)の `edc3060` を別途確認した結果であり、基準ブランチに導入済みとは扱わない。

| 層                                                       | 実装から確認できること                                                                            | 不足・影響                                                                                                         |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `apps/server/src/db/schema.ts` の `circles`              | 団体名・大学名文字列を保存                                                                        | 安定した大学ID、大学の団体コード、年度別担当者プロフィールはない                                                   |
| 同 `incomeRecords` / `expenseRecords`                    | 金額・摘要・発生日・登録日時等。支出は立替への参照と領収書画像への経路を持つ                      | 分類、独立した用途・備考、領収書提出先・番号、制度別判定を保存できない                                             |
| 同 `reimbursementRequests`                               | 件名・支払者名・金額・任意メモ・画像・申請日時を保存                                              | 実購入日・分類・構造化された用途を受け付けない                                                                     |
| `apps/server/src/routes/admin.ts` の承認処理             | 支出の発生日に `reimbursement.submittedAt` を設定                                                 | 3月購入・4月申請を購入年度の支出として抽出できない。元の購入日は保存されていない                                   |
| `apps/server/src/routes/reimbursements.ts` と入力画面    | 立替は件名・支払者・金額・メモ・画像、手動収支は金額・摘要・日付が中心                            | 出力型へ項目を足すだけでは保存・取得経路は増えない                                                                 |
| `packages/accounting-export/src/contracts.ts`            | `ReportEntry` に nullable な `purpose`・`eligibleAmountYen`・`note`、Snapshotの団体情報は名前のみ | 帳票の担当者・領収書提出状況・活動・制度・残高内訳の契約はない                                                     |
| `packages/accounting-export/src/dataframe/validation.ts` | 未分類・未対応科目、日付、金額範囲等を検証                                                        | 用途や対象額がNULLでも通る。大学別の必須判定はない。strictObjectのため任意のメタデータを追加して渡すこともできない |
| PR #2の37件の変換テスト                                  | 合成Snapshotから明細・合計・エラーを検証                                                          | 実書式の必須情報や、入力→保存→承認→再取得の保持を保証するテストではない                                            |

立替のメモ・画像は元申請への参照で取得できるため、承認時に完全に消失するわけではない。ただしメモを用途と同一視できず、画像を保存していても購入日・提出履歴が構造化されるわけではない。ユーザーテーブルの氏名・電話、サークルの権限ロールも、対象年度の記載責任者・大学指定の役職と同一ではない。

## 保存単位と入力タイミング（提案）

次の構成を推奨する。これは追加設計案であり、テーブル名や全大学分の実装を確定したものではない。

| 単位                         | 情報                                                                   | 入力・更新する時点                           | 実装の考え方                                                                                                                   |
| ---------------------------- | ---------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 取引／立替申請               | 実購入日、詳細科目、内訳・用途・備考、領収書の参照                     | 取引登録・立替申請時。過去分は会計担当が補完 | 共通の意味を持つ情報は型付き列で保存。確認済み日付と従来の申請日代用を区別                                                     |
| 領収書と提出先の関係         | 対象年度、申請・制度・イベント報告、提出状態、既知の番号               | 大学への提出時、過去分の確認時               | 型付きの関連テーブル候補。R2画像キーや出力ログに押し込まない。複数の提出関係に拡張できるようにする                             |
| 帳票／制度別の取引判定       | 必要な場合の対象額、判定状態・根拠                                     | 会計担当の確認・査定時                       | `universityId / reportKind / fiscalYear / schemeCode` 等で文脈を特定。全大学共通の対象額1個で上書きしない                      |
| 団体・年度・帳票プロフィール | 団体コード、担当者・所属・学年・大学役職、報告日等                     | 年度設定・提出準備時                         | `circle_report_profiles` 等に、帳票種別とschemaVersionで検証する構造を持つ。現在のログインユーザーから年度の担当者を推測しない |
| 活動・補助金申請／給付       | 日時・場所・人数、外部依頼、イベント報告番号・状態、決定コース・受給額 | 活動記録・申請・受給時                       | 対応大学で必要になった時に実装。初期は型付き年度フォームでもよい。取引のない活動も保持可能にする                               |
| 残高                         | 基準日、開始残高、必要な大学では現金・預金別確認残高                   | 年度開始・期末確認時                         | 初期値0で埋めず、未確認を表現する。科目として当年度収入へ加算しない                                                            |
| 算出値・表示                 | 対象外額、小計・合計、行・ページ番号、表示用の接頭辞やセル色           | Data Frame生成・ファイル生成時               | 根拠が揃うものだけ算出する。過去に提出した番号との対応や番号の意味は保存情報から解決する                                       |

対象額・提出済み状態は取引登録時にまだ決まっていないことがある。全てを初回入力の必須欄にはしない。一方、実購入日や用途は登録時に取得でき、後から失われやすいため先に入力経路を用意する。

`metadata: Record<string, unknown>` だけで保存・解釈する方式は採らない。大学／帳票ごとの型・版・条件付き検証を持ち、検索や関連付けが必要な値には列や外部キーを使う。更新頻度の低いプロフィールにJSONを使う場合も、入出力の両方でschemaVersionに対応する検証を行う。全大学の全項目を取引テーブルに平坦に追加することも避ける。

領収書と取引が複数対複数になる場合は、取引の複製で代用せず、内訳・配賦の関係を追加する。初期対応で1対1に限定するなら、その制約を画面・APIで明示する。どちらにするかは法政の採番・領収書運用の確認で確定する。

## 検証・既存データ・ログとの境界

- 登録時: 日付、金額、科目の所属・収支区分、設定した用途等の型を検証する。大学別に確認できた必須条件を適用する。新規取引に将来の査定額や提出済み状態を要求しない。
- 補完時: 他サークルの取引・申請・領収書・プロフィールとの関連付けを禁止する。公開立替フォームでは申請者が記入する情報だけ受け付け、大学への提出確認や査定結果の変更は管理者側で行う。
- 承認時: 購入日・分類・用途・必要な参照を支出へ保持し、メタデータ欠落や同じ支出の重複生成を防ぐ。承認後の出力元は支出側の確定情報と関連データに一本化し、申請と支出を二重計上しない。
- 出力前: 帳票・年度・制度別の条件付き必須検証を行う。不足は取引IDまたはプロフィール／活動等のIDと項目名に結び付け、修正先を返す。内部メモや学籍番号等をエラーログへ丸ごと出さない。
- 既存データ: 未分類、実購入日不明、用途未記入、提出状態未確認を区別する。申請日を確認済み購入日、未確認対象額を0、未確認提出状態を未提出として移行しない。帳簿の閲覧は維持し、必要な提出出力のみ補完を要求する。
- 制度別対象額: 必要になった場合は未判定と確定0円を区別し、0以上・取引総額以下を検証する。元取引の金額・関連制度を修正した場合は再判定する。
- 履歴: 出力実行ログと、大学へ実際に領収書やイベント報告を提出した事実は別物とする。出力成功だけで「提出済み」へ更新しない。
- 保存範囲: 業務上のプロフィールや領収書提出情報はDBへ保存するが、過去の出力ファイルや入力Snapshot全体を恒久保存する仕様には変更しない。履歴は条件・実行者・版・件数・結果を中心に記録する。

## DB移行

- 取引データを保持する追加変更とし、既存分類はNULLから補完する。
- 既存サークルへの初期項目登録と新規作成時の登録を両方検証する。
- 空DBへの全適用と、既存DBへの新規SQLのみの適用手順を分ける。
- 既存のapply-localを既存DBに全再実行しない。
- 本番適用前に既存データありの移行を検証し、バックアップ・適用順序・アプリの切戻し手順を用意する。
- 同期・変換基盤を含むステージングで動作確認する。デプロイは別途実行作業として扱う。
