## テストの分担

| テスト群         | 環境と検証内容                                                           |
| ---------------- | ------------------------------------------------------------------------ |
| 大学別Data Frame | Vitest。固定Snapshotから、費目・順序・集計対象・期待値を確認             |
| Excelファイル    | Vitestと実ライブラリ。固定Data Frameからセル・式・シート・印刷設定を確認 |
| 再計算・PDF      | 固定コンテナと実エンジン・フォント。数式結果、ページ、日本語、画像比較   |
| DB取得・履歴     | Workers用VitestとローカルD1。実SQL・マイグレーション・テナント制約       |
| 実行処理         | 実D1・実履歴を基本にし、障害を起こすAdapterだけ差し替える                |
| 実行環境間の契約 | Workerと帳票実行環境を接続し、Data Frame検証・版・バイナリ応答を確認     |
| 操作全体         | Playwright。登録・分類・取得・履歴表示と権限                             |

CloudflareのWorkers用Vitest連携を採用し、既存Vite・Wranglerと互換性のある版を導入時に固定する。[公式テスト環境](https://developers.cloudflare.com/workers/testing/vitest-integration/)

## 固定fixture

検証専用テンプレートを1シート2件で用意する。実大学テンプレートの保持テストは別に用意する。

| 入力                                | 期待結果                                         |
| ----------------------------------- | ------------------------------------------------ |
| 支出100・200・300・400・500円       | 3シート、小計300・700・500円、総額1,500円        |
| 開始残高2,000円、上記支出、収入なし | 終了残高500円                                    |
| Excelの100円を150円に変更して再計算 | 総額1,550円、終了残高450円                       |
| 0件                                 | 空書式、サンプル値なし、収支合計0円              |
| 容量2件の費目Aへ3件、Bへ1件         | Aの継続でBが欠落・重複しない                     |
| 同じ取引を集計型へ変換              | 所定の費目に集計され、不要な集計シートが増えない |

入力Snapshot、期待Data Frame、期待金額は独立した固定fixtureにする。本番の変換・集計処理を使って期待値を作らない。

## テストの実装形

以下は擬似コード。固定入力と独立した読取ヘルパーを用いる。

```ts
test("大学指定の費目・順序・集計対象へ変換する", () => {
  expect(buildUniversityDataFrame(fixedSnapshot, fixedDefinition)).toEqual({
    ok: true,
    dataFrame: expectedDataFrame,
  });
});

test("5件を3シートへ分けても明細と総額が一致する", async () => {
  const result = await fileExporter.exportReport(expectedDataFrame, "xlsx", {
    generatedAt: "2026-09-27T00:00:00Z",
  });
  expect(result.ok).toBe(true);
  if (!result.ok) throw new Error(result.error.code);

  const workbook = await readXlsx(result.artifact.bytes);
  expect(readDetailAmounts(workbook)).toEqual([100, 200, 300, 400, 500]);
  expect(readDetailSheetCount(workbook)).toBe(3);
  expect(result.manifest.summary.expenseYen).toBe(1500);
});

test("編集後もExcelの数式が再計算される", async () => {
  const generated = await generateFixtureWorkbook();
  const changed = await replaceFirstExpense(generated, 150);
  const recalculated = await recalculateWithRealEngine(changed);
  expect(readExpenseTotal(recalculated)).toBe(1550);
  expect(readClosingBalance(recalculated)).toBe(450);
  expect(readFormulaErrors(recalculated)).toEqual([]);
});
```

SUM文字列の存在だけで合格にしない。式が残ることと、実再計算の結果が正しいことの両方を確認する。

## 網羅するケース

| 対象     | 必須ケース                                                                         |
| -------- | ---------------------------------------------------------------------------------- |
| 件数     | 0、1、N−1、N、N+1、2N、2N+1、1,000件。Nは各費目ブロックの容量                      |
| シート   | 既存複数シート、3枚以上の継続、記入例・参照シート、印刷改ページ                    |
| 項目     | 初期項目、収支区分、未分類、未マッピング、廃止項目の過去取引                       |
| 日付     | 年度初末日、月末、うるう日、同日複数件、申請日と購入日が別年度                     |
| 状態     | 手動、未承認、承認、精算済み、却下、承認の再試行・競合                             |
| 金額・式 | 費目・全体合計、開始・終了残高、対象額、共有式、他シート参照、二重加算             |
| 文字     | 長文、改行、日本語、式に見える文字列、ファイル名禁止文字                           |
| 権限     | 未ログイン、所属なし、別サークルの取引・履歴                                       |
| 障害     | テンプレート破損・欠落、版不一致、不正Data Frame、変換失敗、タイムアウト、同時出力 |
| 移行     | 空DB、既存DB、分類補完、立替と支出の関連維持                                       |

XLSX全体のZIPや巨大JSONのバイナリ比較を避け、対象セル・式・参照・書式を比較する。代表ケースは生成ライブラリと独立したXML読取等でも確認する。

PDFはページ数・テキスト・金額と画像比較を併用する。最初・中間・最後を含む全ページで欠字・文字切れ・不要な空白ページを確認する。画像比較用のフォント・エンジン・ロケールを固定する。

## D1と実行履歴のテスト

実際のDrizzle SQLをローカルD1へ適用する。migration helperが既存SQLを扱えるか確認し、必要ならstatement breakpointに対応するテスト用ローダーを用意する。簡略スキーマを別に手書きしない。

同一テストファイル内も初期化またはデータ分離する。Workers用Vitestのストレージ分離をテストケース単位と決めつけない。[分離仕様](https://developers.cloudflare.com/workers/testing/vitest-integration/isolation-and-concurrency/)

2サークルを用意して抽出・分類・残高・履歴・結果更新のスコープを検証する。Snapshot取得後に帳票Adapterを停止し、その間にDBを変更して再開するテストで、取得時のData Frameと合計が維持されることも確認する。

| 履歴・障害の状況       | 期待する結果                                     |
| ---------------------- | ------------------------------------------------ |
| 正常終了               | ファイルと履歴の件数・合計・版・ハッシュが一致   |
| 入力不足               | rejected、修正事項、ファイルなし                 |
| 抽出・変換失敗         | failed、段階・実行IDが残る                       |
| 開始履歴失敗           | ファイル生成を実行しない                         |
| 終端履歴失敗           | 成功ファイルを応答しない                         |
| 結果書込の応答喪失     | 読戻しで同じ結果を確認。別結果で上書きしない     |
| 生成・履歴の両方が失敗 | 元の原因と履歴失敗を追跡できる                   |
| 処理ログだけ失敗       | 正常な生成結果を変えない                         |
| 中断                   | 期限後に結果未確認。既存の成功を失敗へ変更しない |
| 再実行                 | 新しい実行ID。前回履歴を維持                     |

状態の条件付き更新・同じ結果の再試行・競合する終端更新も確認する。Data Frame変換は実物を使い、DrizzleやExcelJSの内部操作を大量にモックしない。

## E2E・CI・性能

Playwrightでファイル取得を待ち、取得したファイルも開いて確認する。[ダウンロードの検証方法](https://playwright.dev/docs/downloads)

- 登録・分類からExcel取得と履歴表示。
- 複数ページPDF取得。
- 未分類による拒否、修正後の成功。
- 別サークルの履歴が見えないこと。

通常の開発中は関連テストと型チェックを実行する。各PRでは既存の型チェック・lint・buildと、そのPRの変更に対応する導入済みテストを実行する。Data Frame、Excel、D1、実行処理、実変換、E2Eのテストは各機能の実装と同時に追加し、関連する変更の必須チェックにする。文書のみの変更ではリンク・記述・差分を検証する。テンプレート・フォント・変換処理の変更時は対象大学の再計算と画像比較を必須にする。

テスト用scriptsはtest、test:integration、test:conversion、test:e2eへ整理する。実変換エンジンがないことを理由に必須テストを黙ってskipしない。

1,000件についてDB取得・Data Frame生成・Excel・再計算・PDFを分けて測定する。「数秒以内」は通常起動時p95で5秒以内を暫定目標とし、正式上限は受入条件として確定する。初回起動・同時実行・メモリ・サイズも別計測する。非同期化だけで生成時間の要件を達成した扱いにしない。

## メタデータの保存と大学別の検証

| テスト層       | 実装するケース                                                                                   | 防ぐ問題                                               |
| -------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| 入力API＋D1    | 手動支出・立替の購入日／用途／分類を保存して取得。承認後の支出を再取得して比較                   | 型だけ存在してDB保存や承認の途中で消える               |
| 期間＋承認     | 3月31日購入・4月2日申請を、購入日を要する3月末の帳票へ正しく抽出。旧データの申請日代用は要確認   | 購入日と申請日で年度がずれる                           |
| 法政の純粋変換 | 同じ金額・費目でも領収書提出区分が異なる固定例。物理領収書との番号対応、2シート目への継続        | 全て通常連番にして過去提出分を区別できない             |
| 条件付き検証   | 用途不足、提出区分未確認。対象額の必須性は確認した定義のみに適用し、未知の大学は拒否             | 任意欄の過剰な必須化、または不足を黙認した提出ファイル |
| 対象額         | 運用確定後、未判定／0円／一部対象／全額対象、上限超過、取引額変更時の再確認                      | 不明を0円扱いする、制度間で対象額を流用する            |
| 権限           | 他サークルの科目・領収書・プロフィールのID指定、公開申請から管理者専用の提出確認を書き換える要求 | テナントや入力者の権限を越えて関連情報が混ざる         |
| 学習院対応時   | 助成金種別の内訳、見本に沿う任意備考、年度担当者の切替                                           | まとめて保存した金額を後から根拠なく分解する           |
| 早稲田対応時   | 支出0の活動、提出済みイベント、未申請時の条件、提出済み領収書の費用も収支に含める                | 取引のない活動の欠落、領収書提出状態による費用の欠落   |
| 立命館対応時   | 同じ総残高で異なる現金・預金内訳、未確認残高、担当者未配置時の条件                               | 残高総額から内訳や必須担当者を推定する                 |
| 実行履歴       | 不足時は生成せず結果を記録、正常出力でも領収書を提出済みに更新しない                             | エクスポート実行と大学への提出を混同する               |

金額や個人情報は固定の合成データを使い、提供された記入済みサンプルの実データをfixtureへコピーしない。期待値は変換関数とは独立して書く。大学ルールが未確認の部分は「推測した仕様のテスト」を固定しない。
